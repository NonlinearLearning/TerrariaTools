#### 1. Bytes-per-key / bits-per-key

##### 1a. Theoretical bounds (STATED by sources)

The information-theoretic floor for a **minimal** perfect hash function is log₂(e) ≈ **1.44 bits per key**:

> "Bits per element. For minimal perfect hashing, ε = 0, the lower bound is log e ≈ 1.44 bits per element."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

> "For minimal perfect hash functions the information theoretic space lower bound is log₂e ≈ 1.44 bits/key."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

For a **non-minimal** PHF whose range is m = (1+ε)n the bound is stated as:

> "the space lower bounds is log₂e − ε log((1+ε)/ε) bits/key, minus log(n) bits overall."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

The FKS linear-space result is the O(n) **words** bound:

> "The use of O(n) words of information to store the function of Fredman, Komlós & Szemerédi (1984) is near-optimal: any perfect hash function that can be calculated in constant time requires at least a number of bits that is proportional to the size of S."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

> "The hash function itself requires storage space O(n) to store k, p, and all of the second-level linear modular functions."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

**Important correction:** the FKS citation on the Wikipedia page is *Journal of the ACM* 31(3):538, doi **10.1145/828.1884** — **not** the SIAM DOI `10.1137/0205007` supplied in the task. I fetched the SIAM URL and it returned **HTTP 403 (Cloudflare "Just a moment..." interstitial)**, so I could not confirm what `10.1137/0205007` even is. The FKS *SIAM* paper visible on the page is a different one: Fredman & Komlós, "On the size of separating systems and families of perfect hash functions", SIAM J. Algebraic and Discrete Methods 5(1):61–68, doi **10.1137/0605009**.

##### 1d. gperf — no byte count is reported by the source

gperf **does not report a byte count**. I grepped the full manual text: the string `total_bytes` appears **0 times** and `bytes` appears only in discussions of NUL bytes / `-c` / `len` arguments, never as a memory statistic. The only size-ish diagnostic is under `-d`/`--debug`, and it is an **entry count, not bytes**:

> "total non-linked keys = %d / maximum associated value is %d / maximum size of generated hash table is %d"

**DERIVED FROM SOURCE (not stated by the source)** — gperf's generated table structure and per-key cost. Structure confirmed from the generator itself:

- `asso_values[]` is the "associated values table". The **manual never uses the name `asso_values`** — it calls the table `hash_table`; the actual generated C identifier is `asso_values`:
  > "The associated values table is constructed internally by gperf and later output as a static local C array called 'hash_table'." — https://www.gnu.org/software/gperf/manual/gperf.html
  > `printf ("  static %s%s asso_values[] =\n"` — https://git.savannah.gnu.org/cgit/gperf.git/plain/src/output.cc (line ~864)

  (The manual's `hash_table` name appears stale; I flag this as a documentation-vs-code discrepancy.)
- `asso_values[]` has **`_alpha_size` entries** (one per distinct alphabet byte, ≤ 256), each of `smallest_integral_type(_max_hash_value + 1)` width — i.e. 1/2/4 bytes. This is **O(alphabet), constant in n**, so ≈ 0 bytes/key amortized (~256–1024 bytes fixed total).
- The per-key cost is the **`wordlist[]` array**, indexed by hash value and sized to `_max_hash_value + 1`:
  > `_max_hash_value = (_hash_includes_len ? _max_key_len : 0) + (_asso_value_max - 1) * _max_selchars_length;` — https://git.savannah.gnu.org/cgit/gperf.git/plain/src/search.cc (line ~871)
- Default `-s 1` ⇒ `_asso_value_max ≈ n` **rounded up to a power of 2**:
  > "The default value is 1, thus the default maximum associated value is about the same size as the number of keywords. (For efficiency, the maximum associated value is always rounded up to a power of 2.)" — https://www.gnu.org/software/gperf/manual/gperf.html
- Default element type is a **`char*`**:
  > "the default action is to generate a char * array containing the keywords, together with additional empty strings used for padding the array." — https://www.gnu.org/software/gperf/manual/gperf.html

Putting that together on x64: `wordlist[]` has ≈ `next_pow2(n) × |Pos| + max_key_len + 1` slots × **8 bytes** (pointer). Since `next_pow2(n) ∈ [n, 2n)`, that is **≈ 8 bytes/key when `next_pow2(n) ≈ n`, up to ≈16 bytes/key when `next_pow2(n) ≈ 2n`**, and ×|Pos| more if gperf selects multiple key positions. Add 1 byte/slot if `-l`/`%compare-lengths` is used ("the length table contains as many elements as there are entries in the lookup table"), plus a fixed ~256–1024 bytes for `asso_values[]`, plus the keyword characters themselves.

**⇒ gperf ≈ 64 bits/key (8 bytes/key) best case on x64, typically 64–128 bits/key** — an order of magnitude worse than CMPH, because gperf stores *pointers to keywords*, not a packed minimal encoding. `-S`/`%switch` avoids the array for non-duplicates ("This can lead to a reduction in both time and space requirements for some input files"), but the manual concedes gperf can be wasteful:

> "Another useful extension involves modifying the program to generate 'minimal' perfect hash functions (under certain circumstances, the current version can be rather extravagant in the generated table size)."
> — https://www.gnu.org/software/gperf/manual/gperf.html

The CMPH project states the same conclusion independently:

> "Create very fast hash functions for **small** sets ... As result, cmph can be used to create hash functions where gperf would run forever without finding a perfect hash function, because of the running time of the algorithm and the large memory usage."
> — https://cmph.sourceforge.net/gperf.html

##### 1e. Practical state of the art (STATED)

> "While it is known that just 1.44 bits per key are necessary to store a minimal perfect function, **no published technique can go below 2 bits per key in practice**. We propose a new technique ... which need **1.56 bits per key**, that is, within 8.3% of the lower bound, in less than 2 ms per key."
> — https://arxiv.org/abs/1910.06416 (RecSplit: Minimal Perfect Hashing via Recursive Splitting)

> "For example, with m = 1.23n Belazzougui, Botelho & Dietzfelbinger (2009) achieved a representation size between **3.03 bits/key and 1.40 bits/key** for their given example set of 10 million entries, with lower values needing a higher computation time. The space lower bound in this scenario is **0.88 bits/key**."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

**How many attempts/retries.** The BMZ page gives concrete expected-iteration numbers, and BRZ gives the random-variable model:

> "the runtime has the form [...] for an input of n keys, where [...] is some machine dependent constant ... and Z is a random variable with geometric distribution with mean 1/p = e."
> — https://cmph.sourceforge.net/brz.html

> "Decreasing the value of c leads to an increase in the number of iterations to generate G. For example, for [c = ...] and [c = ...], the analytical expected number of iterations are [...] and [...], respectively, while for [c = 0.93] the same value is around **2.13**."
> — https://cmph.sourceforge.net/bmz.html

So BMZ's retry count is a **geometric random variable**: expected ~1–2.13+ graph-generation attempts, with runtime standard deviation growing linearly in n — "the runtime for a given n has a considerable fluctuation. However, the fluctuation also grows linearly with n" (https://cmph.sourceforge.net/brz.html).

gperf's construction is a multi-step heuristic search, not a single pass:

> "Step 1 (Finding good byte positions): Find a set Pos, as small as possible, such that all tuples (keyword[i] : i in Pos) are different. Step 2 (Finding good alpha increments) ... Step 3 (Finding good asso_values): Find asso_values[c] such that all hash (keyword) are different."
> — https://git.savannah.gnu.org/cgit/gperf.git/plain/src/search.cc

> "In general, gperf assigns values to the bytes it is using for hashing until some set of values gives each keyword a unique value. A helpful heuristic is that the larger the hash value range, the easier it is for gperf to find and generate a perfect hash function. **Experimentation is the key to getting the most from gperf.**"
> — https://www.gnu.org/software/gperf/manual/gperf.html

Note gperf's default is also explicitly **not minimal** — it trades space for speed:

> "By default, gperf attempts to produce time-efficient code, with less emphasis on efficient space utilization."
> — https://www.gnu.org/software/gperf/manual/gperf.html

**CMPH construction memory is not small.** This matters — building the function can cost far more than storing it. BDZ needs ~34.6 bytes/key while generating (c=1.23, b=8) versus 2.61 bits/key to store:

> "Thus, the total memory consumption of BDZ algorithm for generating a minimal perfect hash function (MPHF) is: (28.125 + 5c)n + 0.25cn + (4cn)/(2^b) + O(1) bytes."
> — https://cmph.sourceforge.net/bdz.html

CHM: "(8.125c + 16)n + O(1) bytes" → "33.00n + O(1)" at c=2.09. BMZ: "(8.25c + 16.125)n ... bytes" → "24.80n" (c=0.93). FCH: "O(n) + 9n + 8cn/(log(n) + 1) bytes". (https://cmph.sourceforge.net/chm.html, /bmz.html, /fch.html)

#### 3. The key constraint: why a static key set is required

The set S must be **known in full and fixed before the function is built**, because the function is constructed to be injective *on that specific set* — the displacement/assigned-value tables are solved against the actual keys. Nothing in the structure is derived from a key formula alone.

> "Disadvantages of perfect hash functions are that S needs to be known for the construction of the perfect hash function. Non-dynamic perfect hash functions need to be re-constructed if S changes. For frequently changing S dynamic perfect hash functions may be used at the cost of additional space."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

> "Using a perfect hash function is best in situations where there is a frequently queried large set, S, which is seldom updated. This is because any modification of the set S may cause the hash function to no longer be perfect for the modified set."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

> "For static sets of keys it is possible to compute a function to find any key in a table in one probe; such hash functions are called perfect."
> — https://cmph.sourceforge.net/concepts.html

gperf frames the same constraint as a "static search structure":

> "Conceptually, all insertions occur before any retrievals. ... Search set members, called keywords, are inserted into the structure only once, usually during program initialization, and are not generally modified at run-time."
> — https://www.gnu.org/software/gperf/manual/gperf.html

> "It is therefore frequently worthwhile to expend concerted effort building an optimal search structure once, if it subsequently receives heavy use multiple times."
> — https://www.gnu.org/software/gperf/manual/gperf.html

**Second, harder constraint: keys must be unique.** This is not a style preference — duplicate keys make construction *fail*:

> "The algorithms do not guarantee that a minimal perfect hash function can be created. In practice, it will always work if your input is big enough (>100 keys). The error is probably because you have duplicated keys in the input. **You must guarantee that the keys are unique in the input.**"
> — https://cmph.sourceforge.net/faq.html

> "How do I define the ids of the keys? — You don't. The ids will be assigned by the algorithm creating the minimal perfect hash function. If the algorithm creates an ordered minimal perfect hash function, the ids will be the indices of the keys in the input. **Otherwise, you have no guarantee of the distribution of the ids.**"
> — https://cmph.sourceforge.net/faq.html

That last point is significant: for unordered MPHFs (BDZ, BMZ, BRZ, CHD) you **cannot choose the id/number a key maps to**. If your existing `Dictionary<StructKey, int>` relies on specific integer ids, a perfect hash will not preserve them (CHM is the exception — it is order-preserving: "The resulting MPHFs are order preserving", https://cmph.sourceforge.net/).

Also note **gperf's generated code is C source produced at build time**, so the key set is fixed at *generation* time — effectively compile time for the produced artifact. The manual's phrasing is "static search structure" / "inserted into the structure only once", not literally "compile time", but the generated table is emitted as C literals (`static ... asso_values[] = {...}`, `static ... wordlist[] = {...}`) so it is materialized in the compiled binary.

Caveat on gperf's perfection guarantee: with `-D`/`--duplicates` it is no longer perfect:
> "Using this option usually means that the generated hash function is no longer perfect."
> — https://www.gnu.org/software/gperf/manual/gperf.html

#### 4. The false-positive / verification caveat

**A perfect hash function is only defined on S.** Evaluated on a key not in S it returns *some* in-range integer, and that slot holds a real entry's data — so a naive "hash and read the slot" lookup **silently returns a wrong value instead of a miss**. You must either verify against the real key, or guarantee every query is a member.

The clearest statement of the trade-off:

> "In addition, **if the keys are not in the data and if it is known that queried keys will be valid, then the keys do not need to be stored in the lookup table, saving space.**"
> — https://en.wikipedia.org/wiki/Perfect_hash_function

The contrapositive is the caveat: keys may be omitted from storage **only** when all queries are known-valid. Otherwise you must keep the keys and compare. The lookup recipe confirms the verification step is part of the design:

> "One can then test whether a key is present in S, or look up a value associated with that key, by looking for it at its cell of the table."
> — https://en.wikipedia.org/wiki/Perfect_hash_function

**gperf makes this explicit in its generated API**: it emits **two** functions precisely because the hash alone is insufficient.

> "gperf generates a 0..k element static lookup table and a pair of C functions. These functions determine whether a given character string s occurs in W, using at most one probe into the lookup table."
> — https://www.gnu.org/software/gperf/manual/gperf.html

> "Function: in_word_set (const char * str, size_t len) — If str is in the keyword set, returns a pointer to that keyword. ... Otherwise it returns NULL."
> — https://www.gnu.org/software/gperf/manual/gperf.html

And the generator emits an explicit pre-check plus a full comparison in the miss path:
> "Note that when the hash function is called, it has already been verified that min_key_len <= len <= max_key_len."
> — https://git.savannah.gnu.org/cgit/gperf.git/plain/src/output.cc (line ~853)

**CMPH's API has no membership test at all** — `cmph_search` returns a `uint32` id unconditionally, so verification is entirely the caller's responsibility:
> `unsigned int id = cmph_search(hash, key, (cmph_uint32)strlen(key));`
> — https://cmph.sourceforge.net/ (example code, in-memory vector and in-disk file adapters)

**SPECULATION (my inference, not stated by a fetched source):** the CMPH pages never spell out the false-positive behaviour of `cmph_search` for a non-member key. Given the API surface above (an unconditional integer return, no key argument retained for comparison, and the CHD page's advice to keep "the keys and associated satellite data ... stored in slower but larger memory", https://cmph.sourceforge.net/chd.html), I infer `cmph_search` returns a collision-free but *arbitrary* id for a non-member — you must compare your key against the stored key at that id. I could not find a source that states this in those words.

**Third-party confirmation of the caveat's importance:** this is exactly why `FrozenDictionary` retains keys and hash codes even in its most "perfect-like" strategy — see §5.

Practical implication for your case: a perfect-hash lookup is **two memory touches** (PHF table → stored key bucket → compare), not one. That directly undercuts the memory win unless the verification key is stored compactly (e.g. the struct key is reused, or a small fingerprint/checksum is stored instead of the full key).

#### 5. How .NET's FrozenDictionary string strategies approximate this

`FrozenDictionary` does **not** implement perfect hashing. What it implements is *fingerprint-free bucketing plus explicit verification*, with two strategies that visually resemble perfect hashing (substring keying and length bucketing). The verification step is always present.

**5a. `KeyAnalyzer.AnalysisResults` — exact fields (VERIFIED against source)**

From `https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Collections.Immutable/src/System/Collections/Frozen/String/KeyAnalyzer.cs` (the path in the task, `.../Frozen/KeyAnalyzer.cs`, is **404** — the file lives under `Frozen/String/`):

```csharp
internal readonly struct AnalysisResults
{
    public AnalysisResults(bool ignoreCase, bool allAsciiIfIgnoreCase, int hashIndex, int hashCount, int minLength, int maxLength)
    { IgnoreCase = ignoreCase; AllAsciiIfIgnoreCase = allAsciiIfIgnoreCase;
      HashIndex = hashIndex; HashCount = hashCount;
      MinimumLength = minLength; MaximumLengthDiff = maxLength - minLength; }

    public bool IgnoreCase { get; }
    public bool AllAsciiIfIgnoreCase { get; }
    public int HashIndex { get; }
    public int HashCount { get; }
    public int MinimumLength { get; }
    public int MaximumLengthDiff { get; }

    public bool SubstringHashing => HashCount != 0;
    public bool RightJustifiedSubstring => HashIndex < 0;
}
```

Note: `SubstringHashing` and `RightJustifiedSubstring` are **computed properties**, not stored fields — the stored fields are `IgnoreCase`, `AllAsciiIfIgnoreCase`, `HashIndex`, `HashCount`, `MinimumLength`, `MaximumLengthDiff`. I confirmed the identical struct on `release/10.0` (`.../release/10.0/.../Frozen/String/KeyAnalyzer.cs`), so this applies to .NET 10.

**5b. How the strategy consumes them**

The analyzer searches for the shortest distinguishing substring slice; this is the "approximate perfect hashing" part — the slice is chosen so that it is (near-)unique across keys, making the hash effectively injective on S:

> "The idea here is to find the shortest substring slice across all the input strings which yields a set of strings which are maximally unique. The optimal slice is then applied to incoming strings being hashed to perform dictionary/set lookups."
> — KeyAnalyzer.cs (comments, same URL)

- Substring lengths 1..`MaxSubstringLengthLimit` where `MaxSubstringLengthLimit = 8`.
- Uniqueness bar is **95%, not 100%**: `int acceptableNonUniqueCount = uniqueStrings.Length / 20;` with the comment "Sufficient uniqueness factor of 95% is good enough. Instead of ensuring that 95% of data is good, we stop when we know that at least 5% is bad."
- Tries left-justified first (`comparer.IsLeft = true`), then right-justified when `minLength != maxLength`. Left justification stores a positive `HashIndex`; right justification stores a **negative** `HashIndex` (`comparer.Index = -index - count`), which is exactly what `RightJustifiedSubstring => HashIndex < 0` decodes.
- `HashCount` is the slice length; `HashCount == 1` selects a dedicated single-char implementation.

`FrozenDictionary.cs` then dispatches on those values (`https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Collections.Immutable/src/System/Collections/Frozen/FrozenDictionary.cs`):

> "// Analyze the keys for unique substrings and create an implementation that minimizes the cost of hashing keys."
> `KeyAnalyzer.AnalysisResults analysis = KeyAnalyzer.Analyze(keys, ReferenceEquals(stringComparer, StringComparer.OrdinalIgnoreCase), minLength, maxLength);`
> `if (analysis.SubstringHashing) { if (analysis.RightJustifiedSubstring) { ... RightJustifiedSubstring / RightJustifiedSingleChar ... } else { ... LeftJustifiedSubstring / LeftJustifiedSingleChar ... } } else { ... OrdinalStringFrozenDictionary_Full ... }`

The consuming class hashes **only the slice** and then does a real equality check (`https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Collections.Immutable/src/System/Collections/Frozen/String/OrdinalStringFrozenDictionary.cs`):

```csharp
if ((uint)(key.Length - _minimumLength) <= (uint)_maximumLengthDiff)   // length pre-filter
{
    if (CheckLengthQuick((uint)key.Length))
    {
        int hashCode = GetHashCode(key);
        _hashTable.FindMatchingEntries(hashCode, out int index, out int endIndex);
        while (index <= endIndex)
        {
            if (hashCode == _hashTable.HashCodes[index])
            {
                if (Equals(key, _keys[index]))   // <-- verification; required for correctness
                    return ref _values[index];
            }
            index++;
        }
    }
}
return ref Unsafe.NullRef<TValue>();
```

**The bucket table itself is deliberately *not* perfect.** `FrozenHashTable.Create` picks a prime bucket count targeting a **5% collision rate**, not zero (`FrozenHashTable.cs`):

> `const double AcceptableCollisionRate = 0.05;  // What is a satisfactory rate of hash collisions?`

with `MaxSmallBucketTableMultiplier = 16` / `MaxLargeBucketTableMultiplier = 3` bounding bucket count, and `FindMatchingEntries` returning a contiguous index range to scan. So the design accepts collisions and resolves them by linear scan + `Equals` — the opposite of perfect hashing. Each entry also keeps its full **4-byte hash code** (`int[] HashCodes`) plus a `Bucket[]` (two `int`s per bucket) plus the keys and values.

**5c. The length-bucket strategy (a true "index by length" scheme)**

`https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Collections.Immutable/src/System/Collections/Frozen/String/LengthBucketsFrozenDictionary.cs` — this avoids hashing entirely; the "hash" is literally `key.Length`:

```csharp
int bucketIndex = (key.Length - _minLength) * LengthBuckets.MaxPerLength;
int bucketEndIndex = bucketIndex + LengthBuckets.MaxPerLength;
...
for (; bucketIndex < bucketEndIndex; bucketIndex++)
{
    int index = lengthBuckets[bucketIndex];
    if ((uint)index < (uint)keys.Length)
    {
        if (key == keys[index])       // <-- verification against the real key
            return ref values[index];
    }
    else break;                       // -1 => empty slot
}
```

Constants from `.../Frozen/String/LengthBuckets.cs`: `MaxPerLength = 5`, `EmptyLengthsRatio = 0.2`. It bails out (returns `null` so another strategy is used) if any length bucket would exceed 5 entries, or if fewer than 20% of length buckets are non-empty ("Under this ratio, this implementation won't be used due to too much wasted space"). `-1` marks an empty slot and, cast to `uint`, is `> keys.Length` — that is the miss/verification path.

It handles `byte`, `sbyte`, `ushort`, `short`, `char`, `int`, and **enums with those underlying types**, and computes `min`/`max` of the keys:

```csharp
private const int LengthToCountFactor = 10;
/// "The value of 10 means that up to 90% of the slots in the values array may be unused."
long maxAllowedLength = Math.Min((long)count * LengthToCountFactor, Array.MaxLength);
long length = (long)max - min + 1;
if (length <= maxAllowedLength) {
    if (min == 0 && length == count)  // keys contiguous from 0
        return new WithFullValues<...>(keys, values);       // h(k) = k, no hash table at all
    else
        return new WithOptionalValues<...>(keys, values, optionalValues, min);  // h(k) = k - min
}
```

This is a genuine perfect hash on dense integral keys — `index = key - minInclusive` — and it is where the false-positive caveat is handled explicitly:

```csharp
private readonly struct Optional<TValue>(TValue value, bool hasValue)
{ public readonly TValue Value = value; public readonly bool HasValue = hasValue; }
...
int index = int.CreateTruncating((TKeyUnderlying)(object)key) - _minInclusive;
if ((uint)index < (uint)optionalValues.Length)
{
    ref Optional<TValue> value = ref optionalValues[index];
    if (value.HasValue)          // <-- verification: prevents false positives on non-member keys
        return ref value.Value;
}
return ref Unsafe.NullRef<TValue>();
```

**This is the single most actionable finding for your struct-key scenario.** If your struct keys can be reduced to a dense integral projection (e.g. an enum, or an index with min≈0 and `max-min+1 ≤ 10 × count`), `DenseIntegralFrozenDictionary` gives you array-index lookup with **zero hash table**, a rebuild-free path, and correct misses via `HasValue`. If the spread exceeds 10×count, it declines and you fall through to hashing.

**5e. What happens for the user's struct keys if they are *not* dense integral**

`FrozenDictionary.cs` falls through to `ValueTypeDefaultComparerFrozenDictionary<TKey,TValue>`, which is **not** a perfect hash — it is the general bucketed table with collision scanning and equality verification (`https://raw.githubusercontent.com/dotnet/runtime/main/src/libraries/System.Collections.Immutable/src/System/Collections/Frozen/ValueTypeDefaultComparerFrozenDictionary.cs`):

```csharp
int hashCode = EqualityComparer<TKey>.Default.GetHashCode(key);
_hashTable.FindMatchingEntries(hashCode, out int index, out int endIndex);
while (index <= endIndex)
{
    if (hashCode == _hashTable.HashCodes[index])
    {
        if (EqualityComparer<TKey>.Default.Equals(key, _keys[index]))
            return ref _values[index];
    }
    index++;
}
return ref Unsafe.NullRef<TValue>();
```

Per-entry cost here = key storage + value + **4 bytes hash code** + bucket array (~2 ints per bucket) + the `FrozenHashTable` object. That is roughly 8–16 bytes/entry of pure overhead before keys/values — similar in spirit to `Dictionary`, i.e. **not** the ~2 bits/key a real MPHF would give. (DERIVED FROM SOURCE — I read the fields directly; no byte count is stated by the source.)

#### 6. Summary for the 861 MB / struct-key decision

- **Realistic MPHF storage is 2–4 bits/key** (CMPH BDZ 2.62, CHD 2.07, BRZ ~8.1, FCH <4; RecSplit 1.56). At 2.07 bits/key, 10 M entries ≈ **2.6 MB** of hash-function description versus Dictionary overhead in the hundreds of MB — but that figure **excludes** your stored keys and values, which you must keep for verification.
- **Theoretical floor is 1.44 bits/key**; **no published technique beat 2 bits/key in practice until RecSplit (1.56 bits/key, ~2 ms/key construction)**.
- **gperf is the wrong tool for memory.** No byte count is reported; DERIVED from its generated structure it is ≈ 8 bytes/key (64 bits) best case, and it stores pointers to keywords. CMPH's own comparison page says to use gperf only for "small sets" where you "do not care about memory usage".
- **Construction is expensive and randomized.** Expect retries (BMZ: geometric, expected ~2.13 iterations at c=0.93). Build-time memory is ~25–35 bytes/key for BDZ/BMZ/CHM — i.e. **building an MPHF can transiently cost more than the Dictionary you are replacing.** Budget for that in your 3,861 MB peak.
- **Verification is mandatory** unless every query is guaranteed to be a member. That means keeping the keys (or a compact fingerprint) and doing a compare — realistically **two memory touches per lookup**, which is the main engineering cost of adopting this.
- **In .NET 10 specifically**, check `DenseIntegralFrozenDictionary` first: if your struct keys map to a dense integral range (`max-min+1 ≤ 10 × count`, default comparer, value type), `FrozenDictionary` already gives you perfect-hash-style direct array indexing with proper miss handling and no build-time retry. This is the highest-value, lowest-risk option and requires no third-party dependency. Otherwise .NET has no built-in MPHF, and you would need a native CMPH interop or a managed RecSplit-style implementation.
- **Key set must be static and unique** — the CMPH FAQ is blunt: duplicate keys make construction fail outright.

**Bytes/entry**: Theoretical MPHF floor **1.44 bits/key (0.18 B)**; best practical published **1.56 bits/key (0.20 B, RecSplit)**; realistic floor **~2 bits/key (0.25 B)**; CMPH **CHD 2.07 bits (0.26 B)**, **BDZ 2.62 bits (0.33 B)**, **FCH <4 bits (0.5 B)**, **BRZ 8.1 bits (1.0 B)**, **BMZ 3.72–4.60 B (29.8–36.8 bits)**, **CHM 8.36 B (66.9 bits)** [bytes conversions DERIVED FROM SOURCE]; **gperf ≈ 8 B/key (64 bits) best case, x64** [DERIVED FROM SOURCE (not stated by the source)] — all figures are for the **hash-function description only** and exclude the stored keys/values you must keep for verification, plus gperf additionally stores keyword pointers and CMPH needs ~25–35 B/key transiently to build.

**When it wins**: when the key set is **static, unique, and known before construction**, lookups hugely outnumber updates, you can pay an **offline/one-time construction** whose transient memory (~25–35 B/key for CMPH) may exceed the structure being replaced, and you can afford a **verification compare against the stored key (or a compact fingerprint)** — or can guarantee every query is a member; it loses outright when keys churn (rebuild required: "Non-dynamic perfect hash functions need to be re-constructed if S changes"), when you need to **choose** the id a key maps to (unordered MPHFs assign ids arbitrarily), or when — as with gperf — the implementation stores pointers to keys rather than a packed description. For .NET 10 struct keys, `FrozenDictionary` with `DenseIntegralFrozenDictionary` captures most of the benefit with none of the retry/verification machinery **only if** the keys project to a dense integral range within 10× count.
