# 删除规则分阶段分析约束

## 1. 目的

本文约束本仓库删除规则分析链路里的职责分层，避免把代码片段范围计算、基础结构识别、局部标记、跨结构传播、决策推理混写在同一层。

适用范围：

- `src/Rules/`
- `src/Application/`
- `src/RoslynPrototype/Analysis/`

默认覆盖：

- `RuleDefinition.Mark(...)`
- `RuleDefinition.Propagate(...)`
- `RuleDefinition.Lift(...)`
- `RuleDefinition.Propose(...)`
- `RuleAnalysisHelpers`
- `MarkRegionAnalyzer`
- `PropagationRegionAnalyzer`
- `StructureAnalyzers`
- 删除规则专用分析 API

## 2. 核心原则

### 2.1 先定范围，再原子标记，再语义传播，再标记提升

- 先由 mark 区域 API 计算当前候选所在的代码片段范围。
- 再由 `Mark` 在该范围内调用基础结构分析 API，并结合 CPG / 语义关系产出直接命中的对象级原子标记。
- 再由 propagation 区域 API 计算可传播代码范围。
- 再由 `Propagate` 在该范围内做语义传播，例如赋值右值命中传播到左值。
- 最后由 `Lift` 调用统一标记提升 API，把子表达式标记按规则提升到父表达式或宿主语句。

`Mark` 的最小分析单元是：

- 代码片段
- CPG

这里的代码片段可以是一条语句、一个局部声明、一个条件头部，或其他由 mark 区域 API 明确返回的局部范围。

### 2.2 Mark 只做原子标记

`Mark` 只在当前 mark 区域内产出直接命中的对象级标记，例如：

- 命中以目标对象名为根的表达式
- 命中变量引用、字段访问、属性访问、数组索引、调用点等对象级节点
- 命中定义左值时，可以产出语法上能承载该左值的最小节点，例如 `VariableDeclaratorSyntax`

`Mark` 不把命中提升到父级表达式、语句或控制结构；这些提升统一放在 Mark Lifting 阶段。

禁止在 `Mark` 中做：

- 标记提升
- 跨方法传播
- 跨多个无共同局部宿主的语句传播
- 全图级可达性、调用链、数据流求解
- 无边界祖先 / 后代扫描
- 标记传播
- 最终删除决策推理

### 2.3 四层设计适用于所有 mark 规则

本仓库所有删除规则的 mark 链路都必须按四层设计实现，不允许只在某个规则里局部遵守。

四层设计定义如下：

1. `Mark` 层只产出原子命中。
2. `Propagate` 层负责语义传播。
3. `Lift` 层负责统一标记提升。
4. `Propose` 层只消费 `seedMarks + propagatedMarks + liftedMarks` 形成最终决策。

#### Mark 层全局契约

`Mark` 返回的 `MarkRecord` 必须是当前规则直接命中的对象级节点，典型包括：

- 变量引用；
- 字段访问；
- 属性访问；
- 数组索引；
- 调用点；
- 变量声明器；
- 方法声明等自身就是删除对象的节点。

`Mark` 不允许为了最终 rewrite 方便而提前返回父级语句、控制结构、逻辑表达式宿主或结构尾段。

#### Propagate 层全局契约

`Propagate` 必须以 `seedMarks` 为输入，产出 `PropagatedMarkRecord`。允许的传播包括：

- 赋值右值命中传播到左值；
- 定义初始化右值命中传播到定义承载节点；
- 定义左值命中传播到定义承载节点；
- 调用参数命中传播到调用表达式或调用语句；
- 局部定义传播到同一执行范围内的后续符号引用。

`Propagate` 不产出父级结构提升结果。父级提升必须进入 `Lift` 层。

`Propagate` 可以产出“结构化传播事实”，例如：

- 命中的方法参数所属声明节点；
- 与该参数稳定绑定的调用点集合；
- delegate / lambda / method group / invocation chain 的使用形态归类；
- `TypeSyntax` 命中后稳定映射到的宿主声明；
- 逻辑宿主里的可移除操作数集合；
- `if / elseif / else` 的完整命中态。

但这些传播事实仍然只能表达“传播已经确定的中间态”，不能直接表达最终 rewrite 动作。

#### Lift 层全局契约

`Lift` 必须以 `seedMarks + propagatedMarks` 为输入，产出 `LiftedMarkRecord`。允许的提升包括：

- 成员访问、属性访问、数组索引的子节点命中提升到访问表达式；
- 逻辑表达式子项命中规约或提升到逻辑宿主；
- 子表达式按规则提升到父表达式、语句、循环、`switch`、`if / else` 等宿主结构。

所有父级提升必须通过统一 lifting API 表达；当前默认分析入口是 `src/Rules/MarkLiftingAnalyzer.cs`，统一执行入口是 `src/RoslynPrototype/Lifting/MarkLiftingEngine.cs`。如果某条规则临时不能复用该入口，必须在实现或文档中说明原因和后续收敛路径。

#### Propose 层全局契约

`Propose` 只能消费 `seedMarks`、`propagatedMarks` 与 `liftedMarks`。它可以根据这些 mark 上绑定的语法节点、语义节点和结构信息生成 `Delete`、`Replace`、`Skip` 等决策，但不得重新扫描源码来补一次 mark、传播或提升。

如果 `Propose` 需要结构事实，应优先从 `Mark` / `Propagate` / `Lift` 产物或 `StructureAnalyzers` 暴露的分析结果读取；不得把缺失的 mark 或 lift 逻辑偷偷放回决策层。

`Propose` 可以做的“复杂工作”只限于：

- 最终动作选择；
- replacement syntax 构造；
- conflict key / merge key 收口；
- 同一锚点上的多个候选决策裁决。

`Propose` 不应继续承担下面这些工作：

- compilation-wide 调用点枚举；
- `TypeSyntax` 到宿主声明的大量 ancestor 解析；
- delegate 使用形态归类；
- 为参数收缩、调用点同步或委托同步临时重跑 usage summary。

#### 测试规则也必须遵守

测试里的假规则、回归用例和 diff 资产生成规则同样必须遵守四层设计：

- 测试假规则不得在 `Mark` 阶段手造“已经提升到父级”的 mark；
- 需要模拟语义传播时，应在 `Propagate` 阶段返回 `PropagatedMarkRecord`；
- 需要模拟结构提升时，应在 `Lift` 阶段返回 `LiftedMarkRecord`；
- Mark 相关测试优先断言原子 seed；
- 端到端和 GraphAnalyzer 类测试负责断言最终传播、提升、决策和 rewrite；
- diff 片段必须显示来自哪个单元测试，并保持原始片段和改写片段是完整、独立、合法的 C# 结构或明确的 `<deleted>`。

## 3. Mark 阶段约束

`Mark` 负责：

- 调用 mark 区域 API 计算当前候选代码范围
- 调用 `StructureAnalyzers` 支撑的基础分析 API 识别候选结构
- 结合 CPG / 语义关系判断当前代码是否应被标记
- 返回直接命中的对象级代码节点
- 生成 `MarkRecord`
- 补充规则级原因说明

`Mark` 中可以保留规则特有判断，例如 `IsRootedAtTarget(...)`。这类判断必须满足：

- 判断对象落在当前 mark 区域内
- 不绕过 mark 区域 API 自己手写范围计算
- 不把跨区域关系分析塞进 `Mark`

## 4. Propagate 阶段约束

`Propagate` 负责把 `Mark` 产出的原子标记继续传播到语义相关结构。

`Propagate` 必须先计算传播范围。传播范围用于约束当前 seed mark 能扩展到哪里。

允许做的事：

- 跨 mark 区域标记传播
- 赋值、定义、调用、访问等语义传播
- 基于 `StructureAnalyzers` 的结构间扩展
- 基于 CPG 的控制流、数据流、调用、成员访问等关系分析
- 基于 compilation / semantic model 的稳定调用点、访问点、使用形态和宿主节点收集
- 为后续 `Propose` 生成结构化传播 payload，但 payload 不能携带最终 replacement syntax

`Propagate` 应以 `seedMarks` 为起点，只传播与这些结构标记有关的结构。

`Propagate` 不应绕过 propagation 区域 API 直接做无界祖先 / 后代扫描。

## 5. Lift 阶段约束

`Lift` 负责把 `seedMarks + propagatedMarks` 中已有标记提升到父表达式、语句或控制结构。

允许做的事：

- 通过统一 lifting API 把子表达式标记提升到父表达式、语句或控制结构
- 从已标记结构提升到相关控制结构
- 聚合 `switch section`、`switch statement` 等结构宿主
- 处理 `if / elseif / else` 结构尾段标记

`Lift` 不做新的语义传播，不扫描无关源码补 mark，不产出最终删除决策。

需要 compilation-wide 调用映射、usage summary、delegate 绑定归类或宿主声明收集的逻辑，默认留在 `Propagate`，不要为了省事塞进 `Lift`。

## 6. 分析 API 设计约束

### 6.1 Mark 区域 API

mark 区域 API 必须直接表达：

- 当前候选的语法锚点
- 当前候选允许参与 `Mark` 的代码范围
- 该范围的语法跨度
- 该范围的结构大小

当前默认入口：

- `src/RoslynPrototype/Analysis/otherAnalyzers/MarkRegionAnalyzer.cs`

### 6.2 Propagation 区域 API

propagation 区域 API 必须直接表达：

- 当前 seed mark 的语法锚点
- 当前 seed mark 允许参与传播的代码范围
- 该范围的语法跨度
- 该范围的结构大小

当前默认入口：

- `src/RoslynPrototype/Analysis/otherAnalyzers/PropagationRegionAnalyzer.cs`

### 6.3 基础结构 API

基础结构 API 负责描述代码片段中的结构事实，例如：

- 调用
- 成员访问
- 二元表达式链
- 循环头部
- 赋值和定义结构

当前默认入口：

- `src/RoslynPrototype/Analysis/StructureAnalyzers/*.cs`

基础结构 API 的分析器定义必须自描述。结构实际存在的成员应在分析器实现中有明确建模，不能只靠外部文档说明；公开 `Analyze(...)` 返回值可以保持轻量，只返回调用方当前需要消费的 `AffectedSyntaxTree`。

示例：

- 二元表达式分析器内部应建模根表达式、操作符类型、同类二元表达式层级、叶子操作数，并由公开结果返回受影响语法树。
- 调用 / 成员访问分析器内部应建模调用目标、接收者、参数或访问名等结构成员。
- 循环分析器内部应建模条件、循环体、初始化器、迭代器等结构成员。

## 7. 代码审查口径

评审删除规则相关改动时，至少检查：

- mark 区域是否由专门 API 计算
- propagation 区域是否由专门 API 计算
- `Mark` 是否只在当前代码片段范围内做局部标记
- `Mark` 是否把跨区域结构间推理混进来了
- `Propagate` 是否只承担语义传播
- `Propagate` 若产出结构化 payload，payload 是否只表达中间传播事实而不是最终 rewrite 结果
- `Lift` 是否承担父级提升和结构聚合
- `Propose` 是否只消费三类 mark，不重新扫描补 mark / propagate / lift
- `Propose` 是否又在本地重跑 compilation-wide 调用点扫描、delegate usage summary 或 `TypeSyntax` 宿主解析
- 结构分析器定义是否把可用成员放在实现模型里，而不是只依赖文档说明
- span / 范围计算是否散落在规则私有 helper 中

## 8. 当前仓库的直接落地要求

对当前删除规则原型，默认要求如下：

- `Mark` 的最小分析单元是“代码片段 + CPG”
- 当前 mark 区域由 `MarkRegionAnalyzer` 计算
- 当前 propagation 区域由 `PropagationRegionAnalyzer` 计算
- `Mark` 可调用 `StructureAnalyzers` 支撑的基础分析 API
- `Mark` 只能结合 CPG / 语义关系产出直接命中的对象级标记
- `Propagate` 负责组合 `StructureAnalyzers + CPG` 做跨区域或更复杂的语义传播
- `Propagate` 也是参数收缩、delegate 使用形态、调用点同步这类“中间态收集”的默认落点
- `Lift` 负责通过统一 lifting API 执行父级提升和结构聚合
- `Propose` 只消费 `seedMarks`、`propagatedMarks` 与 `liftedMarks`，不回退成重新识别结构的阶段

### 8.1 参数收缩与调用点同步的补充约束

对 `delete-class` 这类需要同步改声明与调用点的规则，默认按下面分工：

1. `Mark` 只标原子 `TypeSyntax` 或表达式命中；
2. `Propagate` 负责收集所属声明、调用点、访问点、delegate 绑定或其他稳定使用形态；
3. `Lift` 只在需要父级结构宿主时补结构提升；
4. `Propose` 只把这些中间传播事实翻译成 `Replace` / `Delete` 决策。

如果某条 proposal 仍然需要自己：

1. 扫完整个 compilation 找调用点；
2. 重跑 delegate usage summary；
3. 从 `TypeSyntax` 向上重复解析大量宿主声明；

默认视为职责回流，除非在设计文档里明确说明为什么当前无法前移到 `Propagate`。

## 9. 偏离处理

如果某次实现必须偏离本文，说明中至少写清楚：

- 为什么当前逻辑无法用 mark 区域 API 表达
- 为什么这层逻辑必须暂时留在 `Mark`、`Propagate`、`Lift` 或 `Propose`
- 后续是否计划把它回收进分析 API

没有说明的偏离，默认视为分层漂移。
