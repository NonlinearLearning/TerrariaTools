# 规则事实端口类型化：`RuleFactPorts` → `RuleFactKind`

> 状态：阶段 1-3 的内建端口迁移已实现；`RuleSemanticTag` 仍作为自定义测试/legacy 显示 adapter 保留；阶段 4 的只读视图尚未实现。
>
> 读者：修改规则事实合同、规则 DAG 边匹配、传播固定点去重或 binding validator 的维护者。
>
> 范围：将当前由 `RuleSemanticTag` 字符串和 `RuleFactPorts` 静态属性表达的内建事实端口，收敛为可检查的事实 kind；同时保留规则边、执行阶段、固定点区域和证据来源的独立职责。
>
> 不属于本设计：本设计不直接把 Target 和 Flow 拆成两个独立运行时图，也不改变当前 Mark → Propagate → Lift → Propose 的执行顺序。
>
> 更新时间：2026-09-08。

## 决策摘要

当前 `RuleFactPorts` 是一组返回 `RuleSemanticTag` 的字符串常量。它实际承担的是内建事实的分类、端口身份、规则边匹配和 payload 域校验，不是普通的可选 tag。

提议把内建事实身份改为 `RuleFactKind` enum：

```csharp
public enum RuleFactKind : ushort
{
    Unknown,
    TargetExpression,
    TargetTypeSyntax,
    TargetDeclaration,

    FlowLocalDefinition,
    FlowSymbolReference,
    FlowAssignmentTarget,
    FlowLogicalExpression,
    FlowUnaryExpression,
    FlowConditionalExpression,

    RelationDeclarationHost,
    RelationParameterUsage,
    RelationDelegateUsage,
    RelationExtensionUsage,

    LiftExpressionHost,
    LiftLogicalReduction,
    LiftIfStructure,
    LiftSwitchStructure,
    LiftControlStructure
}
```

`RuleFactKind` 本身就是内建事实的唯一类型身份。enum 的底层值不属于协议，也不进入 artifact、replay key 或跨进程数据；这些位置使用 kind 名称（`RuleFactKind.ToString()`），自定义扩展事实才使用 `RuleSemanticTag`。

最终规则合同应直接表达：

```text
RuleFactKind       = 事实是什么、属于哪个内建事实端口
SyntaxKind         = 事实挂在哪类语法节点上
RuleConsumedSyntax = 规则接受什么输入
RuleProducedSyntax = 规则声明什么输出
Edge               = 哪个 producer 可以满足哪个 consumer
RuleRegion         = 规则在哪个执行拓扑区域运行
RuleEvidenceOrigin = 事实由什么证据来源证明
```

`SemanticTag` 这个名称和 `RuleFactPorts` 这个静态类在迁移完成后不再作为内建事实类型的主接口。

## 当前实现和问题

当前实现位于 [`RuleStructureContract.cs`](../../../src/NLISSN.Rule/RuleStructureContract.cs)。它定义了：

- `RuleSemanticTag`，内部保存非空字符串；
- `RuleFactPorts`，集中返回 `Target.*`、`Flow.*`、`Relation.*` 和 `Lift.*` 端口；
- `RuleConsumedSyntax` 和 `RuleProducedSyntax`，以 `SyntaxKind` 加 `RuleSemanticTag` 声明输入输出；
- `RuleStructureContractGraphCompiler`，根据生产端和消费端的 tag 与 syntax contract 建立边。

当前结构有四个问题。

### 字符串承担了名义类型职责

以下两个值在当前类型系统中都是合法的 `RuleSemanticTag`：

```csharp
new RuleSemanticTag("Flow.SymbolReference")
new RuleSemanticTag("Flow.SymbolReferenece")
```

第二个拼写错误只能在边缺失、运行时校验或测试中暴露。内建事实的名字既然是封闭规则合同，就应该由 enum 或等价的受控 ID 表达。

### `RuleFactPorts` 不是完整的端口模型

当前静态类只集中保存值，没有表达：

- 端口所属的语义域；
- 允许的语法形状；
- payload 合同；
- 是否允许跨域；
- 是否参与固定点；
- 是否只允许特定阶段消费。

这些信息仍由 `RuleConsumedSyntax`、`RuleProducedSyntax`、具体 payload 和执行区域分别表达。因此该静态类更像字符串常量表，而不是真正的端口对象。

### `SemanticTag` 名称弱化了真实职责

当前字段实际参与：

```text
producer-consumer 边匹配
MarkRecord 的事实身份
PropagationFactKey 去重
RuleBindingValidator 的 payload 域校验
固定点 worklist 的稳定排序
```

这不是附加描述信息，而是事实的名义类型和路由身份。命名为 `FactKind` 更符合调用者必须理解的契约。

### 自定义 tag 使“纯 enum”需要明确开放边界

当前代码除 `RuleFactPorts` 外还存在：

```text
InternalOnlyPublicMethod.Marked / Propagated / Lifted
UnusedInterfaceImplementation.Marked / Propagated / Lifted
UnreachableMethod
UnreferencedMethod
```

测试规则还使用 `Test.*` tag。`RuleSemanticTag` 的公开构造函数说明当前模型允许任意字符串事实。因此 enum 化不能只替换 18 个常量，还必须决定规则目录是封闭集合还是支持扩展事实。

## 术语边界

| 概念 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| `RuleFactKind` | 识别事实类型和内建端口 | 不决定规则执行顺序 |
| `RuleFactDomain` | 将事实归入 Target、Flow、Relation、Lift 或 Global | 不替代具体 kind |
| `SyntaxKind` | 约束事实对应的 Roslyn 语法形状 | 不识别语义事实类型 |
| `RuleKind` | 区分 Mark、Propagate、Lift、Propose 阶段 | 不表示事实域 |
| `RuleRegion` | 表示普通 DAG、传播固定点或聚合区域 | 不作为事实分类 |
| `RuleEvidenceOrigin` | 表示事实来源，可组合 | 不参与边路由 |
| `Edge` | 表示 producer → consumer 依赖和事实流动 | 不单独完成事实分类 |

`RuleFactKind` 和 `RuleKind` 必须保持分离。例如，一个 `Propagate` 规则可以产生 `Flow.LocalDefinition`；一个 `Lift` 规则可以消费 `Target.Expression` 和 `Flow.SymbolReference`。

## 目标模型

### 内建事实使用 enum

内建规则集合使用扁平、稳定的 `RuleFactKind`。成员名保留语义域前缀，以便代码阅读和生成文档时不丢失上下文：

```csharp
RuleFactKind.TargetExpression
RuleFactKind.FlowSymbolReference
RuleFactKind.RelationParameterUsage
RuleFactKind.LiftIfStructure
```

不使用 `[Flags]`。一个事实只能有一个名义 kind；可组合的是 `RuleEvidenceOrigin` 等来源集合，不是事实类型。

如果 kind 需要写入 artifact、replay key 或跨进程数据，必须使用 `RuleFactKind` 的成员名称，不能直接序列化 enum 的底层值，也不能使用显示文本作为运行时身份。成员重命名属于协议变更；自定义事实继续使用 `RuleSemanticTag.Value`。

### 语义域由显式映射得到

`RuleFactKind` 表达具体事实；需要查询大类时使用单独的 `RuleFactDomain`：

```csharp
public enum RuleFactDomain : byte
{
    Target,
    Flow,
    Relation,
    Lift,
    Global
}
```

`RuleFactKind → RuleFactDomain` 必须是受控的穷尽映射，而不是通过字符串前缀判断。映射缺失时应失败关闭，不能把未知 kind 默认为 `Target` 或 `Flow`。

### 规则合同改为事实 kind

目标形状如下：

```csharp
public sealed record RuleConsumedSyntax(
    IReadOnlyList<SyntaxKind> SyntaxKinds,
    RuleFactKind FactKind);

public sealed record RuleProducedSyntax(
    IReadOnlyList<SyntaxKind> SyntaxKinds,
    RuleFactKind FactKind);
```

`MarkRecord`、`PropagatedMarkRecord`、`LiftedMarkRecord` 和相关 factory 最终使用 `FactKind`，不再把内建事实作为自由字符串保存。

### 边仍然是依赖，不退化为分类表

建边条件保持当前语义，但比较 enum：

```text
producer.FactKind == consumer.FactKind
并且
producer.SyntaxKinds 与 consumer.SyntaxKinds 兼容
```

这只决定“是否允许建立边”。边本身仍负责：

- producer-consumer 依赖；
- cardinality 检查；
- 执行排序和并行释放；
- 下游事实触发；
- 普通 DAG 的拓扑关系。

`PropagationFixedPointRegion` 仍然是显式例外。enum 化不改变固定点收敛协议，也不把递归传播伪装成普通 DAG。

## 事实域和当前规则的对应

enum 化后，当前规则应按有效输入输出合同分类，而不是按文件夹名称分类：

| 规则形态 | 输入 | 输出 | 形态 |
| --- | --- | --- | --- |
| 原子和声明 seed | 无 | `Target.*` | 纯 Target seed |
| 符号引用传播 | `Flow.LocalDefinition` | `Flow.SymbolReference` | 纯 Flow |
| 赋值左值传播 | `Target.Expression` | `Flow.AssignmentTarget` | Target → Flow bridge |
| 定义初始化传播 | `Target.Expression` | `Flow.LocalDefinition` | Target → Flow bridge |
| 对象创建到声明传播 | `Target.Expression` | `Flow.LocalDefinition` | Target → Flow bridge |
| 逻辑表达式传播 | `Target.*` + `Flow.*` | `Target.*` + `Flow.*` | fixed point participant |
| declaration/parameter mapping | `Target.TypeSyntax` | `Relation.*` | Target → Relation bridge |
| expression/if/control lifting | `Target.*` + `Flow.*` + `Lift.*` | `Lift.*` | aggregator |
| 默认删除提案 | `Target.*` + `Flow.*` + `Lift.*` | decision | mixed sink |

这张表是设计分类，不是给边编译器增加新的隐式连接规则。每条跨域连接都必须由具体规则的 `Consumes` / `Produces` 声明产生。

## 扩展事实策略

### 首选：封闭的一方规则目录

如果 NLISSN 的生产规则集合保持仓库内封闭，所有正式事实都进入 `RuleFactKind`，包括可选全局规则事实：

```text
InternalOnlyPublicMethod.*
UnusedInterfaceImplementation.*
UnreachableMethod
UnreferencedMethod
```

测试只测试已声明的规则合同，不向生产 enum 随意增加 `Test.*` 成员。

### 若必须支持外部扩展

如果未来允许外部规则或插件定义新事实，不能重新把任意字符串塞回 `MarkRecord`。应使用受控的内建/扩展引用：

```text
BuiltInFactKind(RuleFactKind.TargetExpression)
ExtensionFactKind(namespace, stableCode)
```

扩展事实必须经过 registry 分配稳定身份、声明所属域和 payload 合同。生产边编译器只接受已注册的事实引用；未知扩展事实失败关闭。

第一版不引入插件扩展，只实现内建 enum。当前 `RuleSemanticTag` 的公共构造函数和测试用 `Test.*` 值是迁移时必须处理的兼容边界，不是继续保留自由字符串的理由。

## 对固定点和去重的影响

当前 [`PropagationFactKey`](../../../src/NLISSN.Core/Propagation/PropagationFactKey.cs) 使用 semantic tag 字符串参与事实身份和 worklist 排序。enum 化后必须直接使用 `RuleFactKind`；自定义事实才回退到 `RuleSemanticTag`：

```text
rule identity
file path
span
syntax kind
fact kind
```

不能因为把字符串换成 enum 就删掉事实 kind；否则不同语义域事实可能在同一 span 上错误合并。

固定点仍需保持：

- 同一事实的去重结果不变；
- seed depth 和 propagation depth 不变；
- source mark 和 evidence 聚合不变；
- worklist 排序稳定；
- DOP 1、2、16 的收敛事实一致。

## 对 binding validator 的影响

当前 [`RuleBindingValidator`](../../../src/NLISSN.Core/Validation/RuleBindingValidator.cs) 根据 payload 类型选择期望关系端口，然后比较 `SemanticTag`。迁移后改为比较 `RuleFactKind`：

```text
MethodParameterUsagePayload
    -> RuleFactKind.RelationParameterUsage

DelegateUsagePayload
    -> RuleFactKind.RelationDelegateUsage

ExtensionMethodMappedCallsitePayload
    -> RuleFactKind.RelationExtensionUsage

DeclarationHostPayload
    -> RuleFactKind.RelationDeclarationHost
```

`BIND014` 的语义必须保持：payload 挂到错误的事实 kind 时，分析失败关闭并报告错误。

## 不采纳的做法

### 继续使用自由字符串，但只集中到 `RuleFactPorts`

这只能减少重复文本，不能提供类型保护，也不能防止业务代码直接构造拼写错误的 tag。

### 用 `SyntaxKind` 代替事实 kind

同一个语法节点可以承载多个事实。例如同一 `IdentifierName` 既可能是 `Target.Expression`，也可能是 `Flow.SymbolReference`。syntax 形状不能替代语义分类。

### 用 `RuleKind` 代替事实 kind

`Propagate` 是执行阶段，不是事实类型。多个 Flow、Target 和 Relation 事实都可以由 Propagate 规则产生。

### 用 `RuleEvidenceOrigin` 代替事实 kind

同一个 `Target.Expression` 可以有不同 evidence origin；当前测试已经证明不同 origin 的事实仍然通过同一个事实端口路由。来源不是事实类型。

### 用两个 enum 隐式推导跨域边

`Target` 和 `Flow` enum 只能说明域，不应自动推导 `Target → Flow` 的业务关系。桥接关系必须由具体规则的输入输出合同声明，否则会重新产生隐式混合图。

## 迁移阶段

### 阶段 0：冻结当前行为

在修改类型前冻结当前基线：

- 规则图节点、边和 fixed-point region；
- `Mark → Propagate → Lift → Propose` 的事实快照；
- evidence、decision、rewritten source 和 diff；
- DOP 1、2、16 的结果。

### 阶段 1：引入 enum 和描述映射

新增 `RuleFactKind`、`RuleFactDomain` 和穷尽 domain mapping。暂时保留 `RuleSemanticTag` adapter，只让内建端口从 enum 映射到旧表示，验证新旧值一一对应。

此阶段不改变图编译、固定点或规则输出。

### 阶段 2：迁移规则合同和事实记录

依次迁移：

1. `RuleConsumedSyntax` / `RuleProducedSyntax`；
2. `MarkRecord` 和所有 mark factory；
3. `RuleStructureContractGraphCompiler`；
4. `RuleGraphCompiler` / `RuleGraphExecutor`；
5. `PropagationFactKey` / `PropagationFixedPointExecutor`；
6. `RuleBindingValidator`、evidence 和测试辅助方法。

属性可以暂时保留旧名称以降低一次性 diff，但内部比较必须使用 enum，不允许新的生产代码构造 `RuleSemanticTag` 字符串。

### 阶段 3：移除内建字符串路由

当生产代码和测试不再依赖内建字符串后：

- 删除 `RuleFactPorts` 静态类；
- 删除 `RuleSemanticTag` 作为内建事实类型；
- 将 `SemanticTag` 重命名为 `FactKind`；
- 对未知 enum 值、未注册扩展值和域映射缺失执行失败关闭；
- 保留显示 formatter，避免 artifact 和诊断失去可读名称。

### 阶段 4：生成语义域和边视图

在事实 kind 稳定后，再生成以下只读视图：

```text
Target seed view
Flow fixed-point view
Relation mapping view
Lift aggregation view
Decision sink view
```

这些是同一规则合同的分层视图，不是未经桥接的两张独立图。

## 验收标准

实现完成前必须满足：

- 内建事实由 `RuleFactKind` 表达，生产路径不再用自由字符串匹配内建端口；
- `RuleFactKind → RuleFactDomain` 映射穷尽且未知值失败关闭；
- `SyntaxKind`、`RuleKind`、`RuleRegion` 和 `RuleEvidenceOrigin` 没有被 enum 混用；
- 同 kind、兼容 syntax 的边仍然建立；不同 kind 的边仍然拒绝；
- `RuleInputCardinality` 行为不变；
- `PropagationFactKey` 的去重、排序和 fixed-point 收敛不变；
- `BIND014` 等错误仍在 payload 绑定错误时报告；
- 逻辑传播的 Target/Flow 混合输出不变；
- DOP 1、2、16 的事实、evidence、decision、rewritten source、diff 和图 telemetry 等价；
- 所有当前正式规则，包括可选全局规则，都有明确事实 kind；
- 如果保留扩展机制，扩展事实具有 registry 身份、域和 payload 合同，不能通过任意字符串绕过注册。

## 当前验证边界

本页的阶段 1-3 已落地：生产规则合同、mark、图匹配、传播固定点 key 和 binding validator 以 `RuleFactKind` 为主身份；`RuleFactKindDescriptor` 提供显示名、domain 映射和未知值失败关闭；`RuleFactPorts`、`BuiltInFacts` 和数值 stable-code 表已删除。`RuleSemanticTag` 只为 `Test.*` 自定义规则和旧 artifact 显示保留，不能再作为生产内建事实路由的入口。

阶段 3 的剩余兼容面是有意保留的 legacy surface：合同和 mark 仍提供显示用 `SemanticTag`，但内建事实比较、payload 校验、固定点身份和正式规则声明均使用 `FactKind`。阶段 4 的 Target、Flow、Relation、Lift 和 decision sink 只读视图尚未生成。
