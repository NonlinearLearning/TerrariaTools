# 测试组件

> 状态：当前设计。
>
> 读者：新增组合 fixture、syntax gate、prerequisite 或最终 diff contract 的维护者。
>
> 责任边界：Testing 只生成和比较测试输入/输出，不执行删除规则，不做 DOP 决策，也不把组合结果解释成生产结论。
>
> 责任：当前仓库维护者。
>
> 更新时间：2026-08-04。

## 本页回答什么

测试组件把多个小源码片段组合成可重放 fixture，并把最终文件结果约束为 Golden 或 Structured diff contract。它解决测试输入和输出的确定性，不替代 [测试策略](testing-strategy.md) 对 Unit、Contract、Host 和 Performance 的分层说明。

## 组件模型

实现位于 `src/NLISSN.Infrastructure/Testing/`：

| 类型 | 责任 | 失败时的结果 |
| --- | --- | --- |
| `TestComponentSource` | 持有规范化相对路径和源码文本 | 根路径、`..` 越界或非法路径拒绝 |
| `TestComponent` | 组合组件 ID、source、semantic/prerequisite 信息 | 重复 ID、缺 prerequisite 进入诊断 |
| `TestComponentComposer` | 按相对文件合并片段，生成 manifest、provenance 并运行 Roslyn syntax gate | 语法错误带组件、文件、span 和诊断 |
| `TestComponentCombinationGenerator` | 按请求的组件数枚举确定性组合 | 只返回 prerequisite-valid 且 syntax-valid 的组合 |
| `TestDiffAssertion` | 比较最终文件字节或结构化 edit 事实 | 返回稳定的字段级失败列表 |

## 组合契约

```text
components
  -> validate IDs and prerequisite DAG
  -> normalize and group relative files
  -> compose source fragments
  -> Roslyn syntax gate
  -> stable manifest and component provenance
  -> Golden or Structured diff assertion
```

composer 先检查重复 ID、缺失 prerequisite 和 prerequisite cycle，再按大小写不敏感的相对路径合并 source，最后解析每个文件并收集错误 span。组合输出保留 file-level provenance，使失败可以回到具体组件；syntax-invalid、prerequisite-invalid 和最终 diff 不匹配不能合并成一个模糊的“fixture 失败”。

最终 contract 分两种：

- **Golden**：比较每个要求文件的完整字节，适合验证格式和完整输出；
- **Structured**：比较 required/forbidden files、文本、edit kind、span 和组件来源，适合验证局部语义且允许非目标格式变化。

组合生成器当前保持全组合 API 和稳定顺序。引入 pairwise/t-wise 或覆盖数组前，必须另行定义因素、取值、seed、覆盖率、生成顺序和 replay manifest；不能静默替换已有集合。

## 限制

测试组件不判断规则是否安全，不保证组成的源码具有完整 compilation 语义，也不负责跨文件项目解析。需要 semantic model、CPG、DOP 或真实目录行为时，应把组合结果交给对应的 Unit、Contract 或 Host fixture，再断言 Mark -> Propagate -> Lift -> Propose -> Rewrite 的外部事实。

失败时保留诊断和 provenance；不要把“没有生成组合”解释成“所有规则都安全”。当前没有把组合数量、语法通过率或 diff 命中率当作生产性能指标。

- `tests/NLISSN.UnitTests/Testing/TestDiffAssertionTests.cs`：Golden/Structured 的文件、文本、span、edit kind 和来源差异；
