# DataFlow 位集稀疏化设计

**状态：已实现并验证（2026-09-23）。** 执行结果见
[稀疏化执行计划 §执行结果](2026-09-23-dataflow-sparse-bitset-execution.md#执行结果2026-09-23-落地全部实测)。
下文 §2–§5 是**设计期**的实测数字（来自 env 门控只读插桩与真实分配测量）；
落地后的**权威实测**为：内存 **33.50×**（稠密 242,467,008 B → 稀疏 7,237,888 B）、
差分验证 **9.51 亿次逐元素比对 0 不匹配**、溢出节点 **2414（0.28%）**。
`k` 的 CPU 代价仍**未与稠密实现对照**（只有 `k=1` vs `k=64` 的同族对照，慢 5–8%）。

**目标：** 把 `DataFlowPass` 的 reaching-definitions 集合表示从"每节点一个定宽稠密位集"
（`N × ceil(D/64)` 个 `ulong`）改为"每节点一个内联稀疏集合"（`N × (1+k)` 个 `int`），
在**不改变任何图语义、候选边、DOP 结果或持久化格式**的前提下，
把**全量**方法的集合存储降低 **32.94×**（设计期实测；落地实测 33.50×），
并把复杂度从 `Θ(N·D/64)` 降到 `Θ(N·k)`。

**范围：** 只改 `src/NLCPG/Builder/Passes/DataFlowPass.cs` 的集合表示与读写路径。
不改 `FactsMatch`/`FactsConflict` 语义，不改 `NLCPGDataFlowOptions` 公开形状，
不改 `NLCPGDataFlowMethodMetrics` 既有字段语义，不改持久化 schema。

**设计依据：** 本文件；前序优化见
[位集压缩设计](2026-09-22-dataflow-bitset-compaction-design.md)。

## 1. 前序状态与剩余问题

前序优化（N→D 压缩 + 消除 `inSets`）已落地并实测，位集存储从 `2·N·ceil(N/64)` 降到
`N·ceil(D/64)`，实测 15.36–29.81×。但它**没有改变复杂度类别**：

| 口径 | 表达式 | 复杂度 |
| --- | --- | --- |
| 原始 | `2 × N × ceil(N/64)` | `Θ(N²/64)` |
| 前序优化后（当前） | `N × ceil(D/64)` | `Θ(N·D/64)`，最坏仍 `Θ(N²/64)` |

`D ≤ N` 只保证收益非负，不保证类别下降。`NPC.AI()` 当前仍是**单块 109.4 MiB**
（`N=122,536`，`wordsPerSet=117`）的 LOH 对象。

**本设计要回答的问题**：能否通过改变算法把类别真正降到对 `N` 线性、且与 `D` 无关。
**答案：能。聚合实测 32.94×，且对最小的方法零成本**（见 §3.2）。

## 2. 实测发现（本设计的事实基础）

**采集口径**：`NLCPGBuilderOptions.CreateDefault()`，`MaxDegreeOfParallelism = 1`，
输入 `D:\TRbackup\Version4\Terraria\{Player,Main,WorldGen,NPC}.cs`，
共 **1692 个方法**，流节点总数 **N = 870,249**。
当前稠密 outSets 合计 **242,467,008 B**。

### 2.1 定律一：`distinctOutSets == D + 1`（1469/1469）

统计每个方法**收敛后 out-set 的不同内容个数**：

| 文件 | 方法数 | 当前 outSets 字节 | 内容去重后字节 | 去重倍数 | `cardMax > 4` | `cardMax > 8` |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `Player.cs` | 398 | 2,085,304 | 179,896 | 11.59× | 6 | 0 |
| `Main.cs` | 127 | 6,475,552 | 960,544 | 6.74× | 1 | 0 |
| `WorldGen.cs` | 662 | 43,283,072 | 3,284,440 | **13.18×** | 62 | 7 |
| `NPC.cs` | 282 | 190,588,040 | 15,761,792 | **12.09×** | 16 | 1 |
| **合计** | **1469** | **242,431,968** | **20,186,672** | **12.01×** | **85** | **8** |

（"内容去重后字节"= `distinctOutSets × wordsPerSet × 8 + 24`，是内容完全去重的理想上界；
它是**备选方案**的测算口径，**不是**本设计内联稀疏的收益——后者见 §3.2。）

**定律一**：在统计到的**全部 1469 个方法**上
**`distinctOutSets == D + 1` 成立率 1469/1469 = 100%**。

### 2.2 定律二：`singletonCount + multiCardinalityCount == D`（1469/1469）

在**全部 1469 个方法**上该式同样 1469/1469 成立。
两条合起来给出真实的集合代数结构：

```
所有不同的 out-set 内容 = { ∅ } ∪ { D 个互不相同的非空集合 }
```

**⚠️ 重要更正（防止误读定律一）**：那 `D` 个非空集合**并不都是单例**。
实测 **691/1469（47.0%）个方法**含有基数 ≥ 2 的集合，最大基数 **12**。
因此"每个程序点最多只有 1 个到达定义"是**错的**，**不得**采用；
成立的是"**不同内容的个数恰好是 `D+1`**"。

**✅ 落地后补充：基数由什么驱动（2026-09-23 实测）**：
out-set 的基数由**同时活跃的参数定义**决定——实测 **`cardMax ≤ 参数个数`
在 1692/1692 个方法上成立**，其中 **74.4%（1259/1692）取等号**。
这解释了 §2.2 的"47.0% 含基数 ≥ 2"：那些方法的参数个数 ≥ 2。

**由此得出一条对测试有直接后果的推论**：要构造"基数 ≥ 2"的 fixture
**必须让方法有多个参数**。纯局部变量构造（单参数 + 多个局部）实测
`cardMax == 1`、`nodesCard2Plus == 0`，**根本不触发 `k=1` 的溢出通道**，
会让"溢出不截断"测试退化为**空测试**（设计期原定的构造正是这样，已证伪并修正）。

### 2.4 关键反直觉发现：稀疏对**大多数**方法反而更大

稀疏存储每行需 `(1+k)` 个 `int` = `4+4k` 字节，稠密在位宽 `w` 时每行需 `8w` 字节。
二者相等当且仅当 `w = (1+k)/2`：

| `k` | 每行字节 | 与稠密持平处 `w` | `w=1` 时（小方法） |
| ---: | ---: | ---: | --- |
| 1 | 8 | `w = 1` | **持平**（都是 `8N`） |
| 2 | 12 | `w = 1.5` | 稀疏大 1.5× |
| 4 | 20 | `w = 2.5` | 稀疏大 2.5× |
| 8 | 36 | `w = 4.5` | 稀疏大 4.5× |

实测按位宽 `w` 分档（`k=4`）：

| `w` 档 | 方法数 | 稠密字节 | 稀疏 `k=4` 字节 | 稀疏/稠密 |
| ---: | ---: | ---: | ---: | ---: |
| **1** | **1580** | 1,852,200 | 4,573,620 | **0.40（更差）** |
| **2** | **56** | 1,095,728 | 1,369,324 | **0.80（更差）** |
| 3 | 14 | 672,744 | 560,676 | 1.20 |
| 4 | 16 | 1,411,072 | 882,064 | 1.60 |
| 31 | 1 | 13,269,264 | 1,070,124 | 12.40 |
| 73 | 1 | 35,991,944 | 1,232,624 | 29.20 |
| 117 | 1 | 114,693,720 | 2,450,744 | **46.80** |

**结论：**
- **`k=4` 时，`w ≤ 2` 的 1636/1692 个方法（96.7%）用稀疏反而更差**——
  它们小到稠密只要 8–16 字节/行。**只有 `w ≥ 3` 的 56 个方法获益。**
- 但收益高度集中：**这 56 个方法占了全部稠密字节的 98.8%**
  （`242,467,008 − 2,947,928 = 239,519,080`）。
- 单方法最大收益（`NPC.AI()`）是 **46.8×**。
  **⚠️ 这是单方法数值，不是聚合收益**（聚合见 §3.2）；混用会导致结论夸大 42%。
- **`k=1` 时该问题消失**：`4+4 = 8 ≤ 8w` 对**任意** `w ≥ 1` 成立，等号仅当 `w=1`。
  即 `k=1` 下**不存在比稠密更差的档位**，因而**不需要**
  "小方法稠密/大方法稀疏"的分流设计。这是选 `k=1` 的决定性理由（详见 §4.4）。
- **"必须分流"这一推论只对 `k ≥ 2` 成立**，不要外推到 `k=1`。

## 3. 目标设计

### 3.1 表示法：内联稀疏集合

用"计数 + 内联槽位"替代定宽位集。采用 **SoA（结构数组）** 而非 `struct[]`：
避免 struct 数组的元素对齐与整体复制开销。

```csharp
private const int InlineSlotCount = 1;   // 由 §3.2 实测裁定

// 始终分配（N 个元素）
private readonly int[] _setCounts;    // int[N]        每节点元素个数（0 合法）
private readonly int[] _setOrdinals;  // int[N * k]    第 i 节点占 [i*k, i*k + count)

// 仅在真的发生溢出时分配（lazy，绝大多数方法为 null）
private Dictionary<int, int[]>? _overflow;  // nodeOrdinal -> 额外序数（升序）
```

**关键设计点（易错）**：`_overflow` **不得**写成 `List<int>?[]`（按节点开引用数组）。
`NPC.AI()` 的 `N=122,536`，一个 `N` 长的引用数组本身就需 `N × 8 = 980,288 B`，
相当于再加 40% 预算。用 lazy `Dictionary<int, int[]>` 时，
**无溢出方法（`k=1` 时 99.72% 的节点）的溢出开销为 0**。

单方法基础存储量：`N × (4 + 4k) + 24` 字节，**与 `D` 完全无关**。

### 3.2 `k` 的实测裁定：`k = 1`

用 `GC.GetAllocatedBytesForCurrentThread()` **真实构造**稀疏存储并测量
（含 lazy 溢出字典），全量 1692 个方法、N=870,249 个流节点的结果：

| `k` | 溢出节点数 | 溢出率（按节点） | 溢出额外序数 | **实测分配字节** | **相对稠密** |
| ---: | ---: | ---: | ---: | ---: | ---: |
| **1** | **2,414** | **0.28%** | **4,967** | **7,361,280** | **32.94×** |
| 2 | 1,255 | 0.14% | 2,553 | 10,690,816 | 22.68× |
| 4 | 297 | 0.03% | 653 | 17,527,448 | 13.83× |
| 8 | 29 | 0.00% | 57 | 31,416,808 | 7.72× |

**裁定：`k = 1`。** 理由：

1. **收益最大且已实测**：32.94× 聚合（`NPC.AI()` 单方法 117×）。
2. **对 `w=1` 的小方法零成本**：`k=1` 每行 8 字节，与稠密 `w=1` 的 8 字节**完全相等**
   ⇒ 小方法既不获益也不亏损，**从而不需要**大小方法分流（§2.4、§4.4）。
3. **溢出率极低**：0.28% 的节点（2414/870,249），额外仅 4967 个序数。
4. `k=4` 虽把溢出降到 0.03%，但收益掉到 13.83×
   （**少省 10,166,168 B，即 2.38×**），而溢出只发生在 0.28%→0.03% 的节点上，
   CPU 代价不对等。

**若 Task 1 实测发现溢出路径的 CPU 代价显著**，回退 `k=4` 仍可用
（13.83× 仍是正收益），但 `k=4` 需接受 `w ≤ 2` 的小方法净亏（§2.4），
届时才需要评估"按 `w` 分流"。

### 3.3 不变式（正确性的全部来源）

正确性**不依赖** §2.1/§2.2/§2.3 的经验定律——那些只决定收益倍数。
正确性由以下 6 条不变式保证：

| # | 不变式 | 违反后果 |
| ---: | --- | --- |
| 1 | **双射**：稀疏表示与定宽位集一一对应，可互相还原 | 集合内容错 |
| 2 | **溢出外溢，绝不截断**：第 `k+1` 个元素写入 `_overflow` | **静默丢靠后的定义** |
| 3 | **严格升序且无重复**：序数按升序存储、元素唯一 | 见 §3.5（预算误触、整方法丢边） |
| 4 | **精确相等**：`SetEquals` 逐元素精确比较 | **fixpoint 提前收敛** |
| 5 | **空集可表示**：`count == 0` 是合法高频状态 | 语义错（实测 93.9% 为空） |
| 6 | **溢出只影响表示，不影响语义**：绝不改 `OverflowReason` | 改为报告失败/丢边 |

### 3.4 单调性论证（`k` 不会在 fixpoint 中途被击穿）

一个自然的担心：`k` 按**收敛后**的 `cardMax` 选定（`k=1` 时 47.0% 的方法会溢出），
但迭代**中途**的集合可能更大。**该担心不成立**，但**理由必须写对**。

**⚠️ 错误的理由（不要用）**：不能说"`outSets` 在循环内从不清除，所以单调递增"。
`CopyBitSet`（`DataFlowPass.cs:953`）是**覆盖写**，它把 `outSets[v]` 整体替换为
`updatedScratch`；而 `ApplyDefinitionTransfer`（L1003）会清掉冲突位，
所以**新算出的值在数值上可能比旧值小**。仅凭"不清除"推不出单调性。

**正确的理由（Kleene / 混沌迭代不变式）**：设 `F` 为整个方程组的一次求值，
`F_v(x) = gen_v ∪ (in_v(x) − kill_v)`，其中 `in_v(x) = ∪_{p∈preds(v)} x[p]`。

1. **`F` 单调**：`in_v` 对每个 `x[p]` 是并集 ⇒ 单调；`S ↦ gen ∪ (S − kill)` 单调。
2. **起点是 ⊥**：`outSets` 是新建零数组（L663），全部节点入队（L668-672）。
3. **不变式 `x ≤ F(x)` 在每次赋值后保持**：若赋值前 `x ≤ F(x)`，
   则对节点 `v` 做 `x[v] := F_v(x)` 时，由 `x ≤ F(x)` 得 `旧 x[v] ≤ F_v(x)`，
   故 `x[v]` **不减**；再由 `F` 单调，`x ≤ F(x)` 继续成立。
4. **有限格 ⇒ 终止于最小不动点**：`x` 沿递增链上升，格有限故必停；
   停止时 worklist 为空 ⇒ 无节点会变 ⇒ `x = F(x)`。
   混沌迭代从 ⊥ 沿递增链到达的不动点即 **lfp**（这也解释了跨 DOP 的图等价性）。

由 1–4：**每个节点的值在迭代过程中单调不减**（尽管单次转移本身可以"清位"）
⇒ `in` 集只增不减 ⇒ **任意中途时刻的基数 ≤ 收敛后的基数**。

**诚实标注**：这是**从代码结构与标准数据流定理推导**的，
**没有插桩实测中途基数**。执行计划 Task 1 要求实测验证该推论；
若实测推翻，则 `k` 必须按中途峰值 + 安全裕量选取。

**✅ Task 1 已实测验证（2026-09-23）**：全量 1692 方法 / N=870,249 上，
中途基数**从未超过**收敛基数（`worseNodes` 恒为 0，
`midMax == finalMax == 12`，`midSum == finalSum == 71,899`）⇒ 推论**成立**。

**⚠️ 但该验证的区分力很弱，不得夸大**：实测 `worklistIterations / N = 1.0000`
（1688/1692 个方法恰好等于 N；全语料总重复处理仅 **15** 次），
即该语料上 fixpoint 近乎**单趟收敛**，多数节点只被写入一次，
单调性近乎**平凡成立**。因此：

- 本条**不能**推广为"任意语料/任意 CFG 下 `k=1` 都安全"；
- 它也不是反面证据；
- 真正的正确性保证来自**溢出外溢设计**（基数超出 `k` 只是进溢出字典，不是错误）
  与 Task 5 的差分验证（9.51 亿次比对 0 不匹配）。

**附带发现（解释了 §2.3 的基数分布）**：out-set 基数由**同时活跃的参数定义**驱动——
实测 `cardMax ≤ 参数个数` 在 **1692/1692** 成立（74.4% 取等号）。
这同时说明：构造"基数 ≥ 2"的测试 fixture **必须多参数**，
纯局部变量构造实测 `cardMax == 1`、**不触发溢出**。

### 3.5 保序为什么是正确性要求（而非风格）

`NLCPGDataFlowOptions.MaxCandidateEdgesPerMethod` **默认是 `int.MaxValue`**
（`NLCPGBuilderOptions.cs:153`），默认路径不受影响。但一旦配置了预算，顺序就决定结果：

1. `DataFlowCandidateCollector.TryAdd`（L133）在**去重之前**就自增
   `RawCandidateCount`（L135）并与预算比较（L136）。
2. 当前枚举顺序由 `EnumerateSetBits`（L984）的 `TrailingZeroCount` 保证**升序**。
3. 若稀疏版改用 `HashSet<int>`/`Dictionary` 存储，迭代顺序改变 ⇒
   `RawCandidateCount` 触顶的时机改变 ⇒
   `CreateCandidateLimitExceededPartition`（L857）被触发时返回的是
   **`new LocalFlowCandidateSet(Array.Empty<CpgEdgeCandidate>())`（L871）——
   该方法的全部 DataFlow 边被丢弃**（且 `OverflowBehavior` 默认 `SkipMethod`）。

即：**顺序偏差不会"少一条边"，而是在预算路径上整方法丢边**。
所以序数必须**升序存储**（不变式 3），且 `AddReachable`（L216）与
`EnumerateSetBits` 的产出顺序必须与稠密版一致。

### 3.6 操作映射（全部调用点已核对）

| 现操作 | 定义行 | 调用点 | 稀疏实现 | 复杂度变化 |
| --- | ---: | --- | --- | --- |
| `OrBitSet` | L945 | L686, L729 | 有序归并去重 | `O(ceil(D/64))` → `O(k)` |
| `CopyBitSet` | L953 | L708 | 计数+槽位复制 | `O(ceil(D/64))` → `O(k)` |
| `BitSetEquals` | L958 | L703 | **逐元素精确比较** | `O(ceil(D/64))` → `O(k)` |
| `IsBitSetEmpty` | L971 | L733 | `count == 0` | `O(ceil(D/64))` → `O(1)` |
| `EnumerateSetBits` | L984 | L761 | 顺序扫描（天然升序） | `O(ceil(D/64))` → `O(k)` |
| `IsBitSet` | L940 | L229 | 线性扫描（`k=1` 时 1 次比较） | `O(1)` → `O(k)` |
| `ApplyDefinitionTransfer` | L1003 | L695 | 过滤冲突 + 有序插入 | `O(ceil(D/64) + bits)` → `O(k)` |

`IsBitSet` 是**唯一变慢**的操作（`AddReachable` 用它做成员测试）。
`k=1` 时它是 1 次比较，实践上不构成退化；但**未实测**。
除它以外所有操作都从"按位宽 `ceil(D/64)` 线性"降为"按基数线性"，
故**预期 CPU 不退化**（`NPC.AI()` 的 `w=117` vs `k=1`）。同样**未实测**。

## 4. 必须正面处理的约束

### 4.1 `WordsPerSet` 语义保持不变（兼容性裁定）

`WordsPerSet` 已落盘到性能摘要 JSON（`SchemaVersion = 1`），
且 `NLISSN.HostTests` 断言 `schemaVersion == 1`。

**裁定**：`WordsPerSet` 继续表示**逻辑位宇宙宽度** `ceil(D/64)`，**不随稀疏化改变**。
理由：稀疏化是**内部表示**变化，不改变"位宇宙有多大"这个逻辑事实；
`WordsPerSet` 是逻辑量而非存储量。这样：

- 不升 `schemaVersion`，HostTests 断言保持；
- `NLCPGPartitionedBuilderTests.cs:276` 的断言
  `Assert.Equal((runMetric.DefinitionCount + 63) / 64, runMetric.WordsPerSet)`
  **保持通过，无需修改**；
- 代价：该字段**不再反映实际存储量**。必须在字段注释与
  `设计docs/目前设计/性能分析组件.md` 写明，
  并**不得**再用 `WordsPerSet` 推导内存（前序设计 §3.4 表格的口径现已失效）。

### 4.2 溢出可观测性

溢出是内部表示问题，**不得**写入 `NLCPGDataFlowOverflowReason`
（那会改变 `OverflowBehavior` 行为与图内容，违反不变式 6）。

在 `NLCPGDataFlowMethodMetrics` 增加一个**带默认值**的可选字段记录溢出节点数：

```csharp
int SparseOverflowNodeCount = 0
```

带默认值 ⇒ 既有 8 参构造点全部不变（`NLCPGBuildMetrics.cs:107-115`）。
该字段**不映射**到 `CpgPerformanceFactMapper` / `PerformanceSummaryDocument`，
因而不触碰持久化格式。只用于测试与诊断。

### 4.3 无 `InternalsVisibleTo` 的验证约束

`src/NLCPG` **没有任何 `InternalsVisibleTo`**（全仓 17 处，
全部位于 `src/NLISSN*` 与 `tests/NLISSN.Testing`）。

**裁定**：**不新增** `InternalsVisibleTo`（会扩大程序集边界，
且 `tests/NLISSN.ContractTests/Architecture/ArchitectureBoundaryTests.cs` 对
程序集可见性有既有断言）。因此：

- 契约测试只能经 `NLCPGBuilder` 公开 API 观测（图快照 + `LastBuildMetrics`）。
- 稠密↔稀疏的**逐元素差分验证**用**临时 env 门控探针**完成（同 §5.1 手法），
  验证后删除，不进入产品代码。

### 4.4 小方法不获益的问题在 `k=1` 下自动消失

§2.4 显示 **`k=4`** 时 `w ≤ 2` 的 1636/1692 个方法用稀疏更差
（因为 `k=4` 每行 20 字节 > 稠密 `w ≤ 2` 时的 16 字节）。
但**这个结论不适用于 `k=1`**，理由是纯代数的：

```
稀疏（k=1）每行 = 4 + 4×1 = 8 字节
稠密     每行 = 8w 字节
⇒ 稀疏 ≤ 稠密，等号当且仅当 w = 1
```

**即 `k=1` 时不存在任何"更差"的方法**：`w=1` 完全持平，`w ≥ 2` 严格更省。
按实测的按 `w` 分档数据（§2.4 表）复算，下表为 **`w ≤ 8` 子集**
（合计稠密 7,961,288 B，占全量 242,467,008 B 的 3.3%）：

| `w` | 方法数 | 稠密字节 | 稀疏 `k=1` 字节 | 差值 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1580 | 1,852,200 | 1,852,200 | **0（持平）** |
| 2 | 56 | 1,095,728 | 548,536 | 省 547,192 |
| 3 | 14 | 672,744 | 224,472 | 省 448,272 |
| 4 | 16 | 1,411,072 | 353,056 | 省 1,058,016 |
| 5 | 3 | 486,992 | 97,456 | 省 389,536 |
| 6 | 5 | 1,276,392 | 212,832 | 省 1,063,560 |
| 7 | 2 | 549,408 | 78,528 | 省 470,880 |
| 8 | 2 | 616,752 | 77,136 | 省 539,616 |
| **小计** | **1678** | **7,961,288** | **3,444,216** | **省 4,517,072** |

更大的 `w` 档（17/18/19/26/31/33/43/73/115/117）每行节省 `8(w−1)` 字节，
是收益的主要来源；`k=1` 下它们同样严格更省。

**裁定：**

- **不引入**"按 `w` 分流两种表示"的复杂度——`k=1` 下**没有任何方法需要分流**，
  全局最优就是纯稀疏。
- §2.4 中"需要按大小方法分流"的推论**仅对 `k ≥ 2` 成立**；
  `k=1` 使该问题消失，这正是 §3.2 选 `k=1` 的第二个理由。
- 若 Task 6 实测显示换语料后出现回归（理论上不可能，因上式对任意 `w ≥ 1` 成立），
  应优先怀疑溢出路径开销或统计口径，而非引入分流。
- 溢出开销的实测值：无溢出时纯稀疏为 `24×1692 + 8×870249 = 7,002,600 B`，
  含溢出实测 **7,361,280 B** ⇒ 溢出仅占稀疏总量的 **4.87%**（358,680 B）。

## 5. 实测基础与验证边界

### 5.1 本文实测数字的来源（可复现）

用 **env 门控的只读插桩**测得，分三次：

1. **内容去重与基数分布**（§2.1–2.3）：在 `AnalyzeCfgSensitivePartition` 的
   fixpoint 之后插入 `ProbeVerify`，`NL_DFVERIFY=1` 时执行，只读 `outSets`。
   输出 `distinct / singletonCount / multiCardinalityCount / cardMax / empty`。
2. **聚合字节对比**（§2.4）：`ProbeAgg`，`NL_DFAGG=1`，按每方法
   `24 + 8·N·w`（稠密）与 `24 + 8·N`（`k=1`）等求和，并按 `w` 分档。
3. **真实分配测量**（§3.2）：`ProbeOverflow`，`NL_DFOVER=1`，
   对 `k ∈ {1,2,4,8}` **真实构造** `int[N]` + `int[N*k]` + lazy `Dictionary<int,int[]>`，
   用 `GC.GetAllocatedBytesForCurrentThread()` 前后差得到实测分配字节。
   ——这一项是**实测**（非模型估算），且**含溢出开销**。

**插桩未改变任何语义**；测完删除。`DataFlowPass.cs` 已还原并核验：

```
SHA256 = 278F1C005923CA9508535903430EB7043891B45447C3E2E7B869F989552E6557
```

（与前序优化完成态逐字节一致），`Probe|NL_DF` 残留检索为空；
探针工程与临时目录（`Build\tmp\df*`）已删除（`Build/` 本就被 gitignore）。

### 5.2 能证明

- **逐步相同**：若不变式 1（双射）与 3（保序）成立，则稀疏版与稠密版
  **每一次迭代、每一个 kill 决策、每一次枚举产出都逐位相同**，
  下游图自然相同。这是构造性结论，强于"结果等价"。
- **图等价**：既有 12 个 oracle（`NLCPGPartitionedBuilderTests` 的 5 个 DataFlow
  跨 DOP 测试 + `CpgWorkBatchDataFlowTests` 的批次等价 + 其余图等价断言）。
- **内存下降**：§3.2 是**真实分配测量**（同输入/同配置/同 runtime），
  可作为收益基线；但落地后仍需按 Task 6 重测**端到端**分配量。

### 5.3 不能证明 / 必须额外测量

> **落地后更新（2026-09-23）**：本小节的多数"未测"项已在执行阶段补测，
> 结论见 [执行计划 §执行结果](2026-09-23-dataflow-sparse-bitset-execution.md#执行结果2026-09-23-落地全部实测)。
> 保留原文以便追溯设计期的诚实边界。

- **CPU 影响**（§3.6 的预期是方向性判断，未测）。
  → 落地后部分补测：`k=1` 比"溢出恒不发生"的 `k=64` 慢 **5–8%**（NPC.cs，同机同轮）；
  **但仍未与稠密实现对照**，故仍不得声称"CPU 无退化"。
- **`k` 的最终取值**：§3.2 的裁定基于内存实测，**未含 CPU 代价**。

- **中途基数 ≤ 收敛基数**（§3.4 是结构推导，未插桩实测）。

- **整轮 gcdump 前后对比**：前序优化遗留的未完成项，本次仍不做（见 §6）。

## 6. 不做的事（明确排除）

| 排除项 | 理由 |
| --- | --- |
| **版本化共享 / copy-on-write** | **实测否决**：`NPC.AI()` 的 `bytesShared=117,082,072` > 当前 `114,693,720`（§2.3） |
| **需求驱动（只为被查询节点求解）** | **实测否决**：`queried/N ≈ 1.00`（`122814/122536`） |
| **`k ≥ 2` 作为默认** | **实测否决**：`k=1` 给 32.94× 且对 `w=1` 零成本；`k=4` 只有 13.83× 且小方法净亏（§2.4、§3.2） |
| **按 `w` 分流（小方法稠密/大方法稀疏）** | 不必要：`k=1` 下稀疏 ≤ 稠密对**任意** `w ≥ 1` 成立（§4.4），全局最优即纯稀疏；双路径只增加正确性风险 |
| **SSA / def-use 换范式** | 本 pass 依赖 `LocationKey`/`BaseKey`/`PathKey` 的别名与冲突启发式，字段/属性访问不是纯 SSA；换范式会**改变边集**，与"图等价"验收直接冲突 |
| **内容去重/interning** | 实测 12.01×，**低于**内联稀疏的 32.94×；且需内容哈希与不可变 payload，风险更高。**留作备选**（§8） |
| **改 `FactsConflict`/`FactsMatch`** | 属语义变更，与"纯表示层"目标冲突；§2.1 的疑点需独立立项 |
| **升 `SchemaVersion`** | 会破坏 `PerformanceSummaryWriterTests` 断言 |
| **加 `InternalsVisibleTo`** | 见 §4.3 |
| **`ArrayPool` 复用** | 前序已实测否决（`Rent` 向上取整到 2 的幂导致 1.54×） |
| **整轮 gcdump A/B 对比** | 前序遗留项；本次以"真实分配测量 + 同输入 A/B"为准，保持口径一致即可对比 |

## 8. 备选与后续

1. **内容去重/interning（备选，实测 12.01×）**：`outSetId[N]`（4N 字节）
   + 内容池 `distinct × (4 + 4k)`。它与内联稀疏**可叠加**：
   `NPC.AI()` 估算 `4N + distinct×(4+4k)` = 490,144 + 7452×8 = 549,760 B。
   但需要内容哈希与**不可变 payload**（共享对象被原地写会污染所有共享者——
   前序讨论已列为高风险）。**建议在稀疏化落地并验证后，作为独立增量评估。**

2. **§2.1/§2.2 定律的独立排查**：两条定律在 1469/1469 上成立但原因未明，
   值得查清"是语义正确的自然结果，还是精度缺陷"。
   **不属本计划范围，但必须在 Task 1 记录结论。**

3. **整轮 gcdump A/B**：前序遗留项，用于回答"优化后峰值堆第一名是谁"。
