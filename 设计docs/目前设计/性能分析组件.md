## 1. 目标和边界

目标是在不改变分析语义、图身份、规则输出和写回结果的前提下，把一次分析拆成可解释、可比较、可复盘的性能证据：

```text
输入身份与环境
    -> Workspace / input load
    -> CPG build and persistence
    -> RuleGraph Mark / Propagate / Lift / Propose
    -> rewrite / diff / evidence / write-back
    -> stable summary and optional diagnosis attachments
```

组件只负责性能事实的采集、聚合和输出，不负责：

- 修改规则选择、CPG capability 或并发策略；
- 判断删除是否安全、改变 decision 或改写内容；
- 取代 `dotnet-trace`、`dotnet-counters`、`dotnet-gcdump` 等外部诊断工具；
- 把一次运行的偶然下降宣布为性能回归修复；
- 把并发操作的累计耗时当成端到端 wall time。

## 2. 设计结论

外部项目给出的可迁移结构和本设计的决定如下：

| 外部证据 | 本设计决定 |
| --- | --- |
| LLVM `llvm-mca` 用 pipeline、event listener 和多个 View 组织分析 | 语义组件发布窄性能事件；summary、resource、rule hotspot 和诊断输出分开实现 |
| LLVM `llvm-exegesis` 分离 executor、重复采样、validation counter 和 aggregator | `normal`、`diagnostic`、`profile`、`benchmark` 是显式模式；聚合策略不能隐藏在单个 elapsed 字段里 |
| LNT 分开 compile、exec、profile、diagnose，并把 warmup/drop 样本写入工具契约 | 样本身份和预热语义必须写入报告；profile 和 gcdump 不进入普通测量中位数 |
| LLVM Test Suite 同时记录时间、RSS、代码尺寸和诊断 flags | 阶段时间必须与 allocation、GC、working set、图规模和制品大小同级输出 |
| Roslyn benchmark 用 setup、Params、baseline 和 MemoryDiagnoser 控制输入形态 | 微基准只测固定 semantic query、materialization 或 cache 行为，不能替代端到端 harness |
| Joern 按文件收集 duration，输出前稳定排序，并显式区分有限并发路径 | 每个 source item 有稳定 identity，聚合前不依赖并发完成顺序 |
| CodeQL 将 join-order badness 和缺失性能注解做成可执行规则 | 未来增加性能告警和自校验，但告警不直接改变分析语义 |

## 3. 组件结构

初版只引入性能域的词汇和边界，不先引入通用 profiler 框架：

```text
PerformanceMeasurementSession
  |-- input/environment identity
  |-- sample mode and sample number
  |-- StageMeasurementScope
  |     |-- wall elapsed
  |     |-- resource deltas
  |     |-- semantic/output counters
  |     `-- completion status
  |-- PerformanceEventSink
  |     |-- low-overhead runtime events
  |     `-- optional diagnostic events
  `-- PerformanceReportAggregator
        |-- per item and per stage summary
        |-- p50/p95 and normalized values
        |-- hotspot ranking
        `-- equivalence and completeness checks
```

建议的最小职责：

1. `PerformanceMeasurementSession` 固定一次 run 的身份、环境和模式；它不执行分析。
2. `StageMeasurementScope` 包住一个已存在的阶段边界，记录开始前后的计时器和资源快照；它不持有 CPG 或规则对象。
3. `PerformanceEventSink` 接收不可变事件。sink 失败只能丢弃诊断数据，不能让分析失败。
4. `PerformanceReportAggregator` 只消费事件和最终结果快照，计算聚合值，不重新访问 semantic model。
5. `PerformanceReportWriter` 输出稳定排序的文本和 schema 化 JSON；同一组统计数据驱动两种格式。

这些名称是初版设计词汇，不代表本轮已经新增对应 C# 类型。

## 4. 身份和数据契约

### 4.1 Run identity

每一份报告必须能回答“测了什么、用什么测、结果是否可比较”：

| 字段 | 语义 |
| --- | --- |
| `schemaVersion` | 性能报告格式版本，不与 CPG schema 混用 |
| `runId` | 当前 artifact run 的稳定关联键 |
| `gitCommit` | 被测 NLISSN commit；外部仓库 commit 只记录在研究来源 |
| `inputKind` / `inputPath` | direct file、directory、project 或 solution |
| `inputIdentity` | source hash、fixture manifest hash 或 project/TFM identity |
| `ruleProfileHash` | 规则选择和配置的稳定指纹 |
| `capabilityFingerprint` | CPG capability build plan 的稳定指纹 |
| `cacheMode` | cold、warm、persistence hit、persistence miss 或 disabled |
| `sdk` / `runtime` / `os` / `cpu` | 环境指纹；未知值不得伪造为默认值 |
| `directoryDop` / `cpgDop` / `ruleDop` | 分层并发配置，不能压成一个 `dop` |
| `mode` / `sampleNumber` / `isWarmup` | 运行模式和样本语义 |

输入 identity 和配置 fingerprint 是比较前置条件。任何一项不一致，报告应标记为不可比较，而不是静默合并。

### 4.2 Stage sample

阶段事件至少包含：

| 字段 | 语义 |
| --- | --- |
| `stageId` | 稳定阶段名，例如 `WorkspaceLoad`、`CPG.Syntax`、`CPG.Operation`、`Rule.Propagate` |
| `parentStageId` | 阶段树中的父节点；没有父节点时为 null |
| `itemId` | 文件、项目、规则节点或 artifact item 的稳定 identity |
| `wallElapsedMs` | 该 scope 的端到端墙钟耗时 |
| `accumulatedElapsedMs` | 并发子操作的累计工作量；不能替代 wall time |
| `allocatedBytesDelta` | scope 前后 `GC.GetTotalAllocatedBytes` 差值；不是 retained heap |
| `workingSetBytes` / `gc0Delta` / `gc1Delta` / `gc2Delta` | 可选资源快照和 GC 增量 |
| `queueWaitMs` / `peakActive` / `peakBuffer` | 并发池诊断字段；只对有意义的阶段填充 |
| `inputCount` / `outputCount` | 规则节点或 pass 的输入输出数量 |
| `nodeDelta` / `edgeDelta` / `artifactBytes` | 结果规模和制品规模 |
| `status` / `errorKind` | completed、failed、cancelled 或 skipped |

未知值用 null 表示，真实测得的零才写零。阶段名和字段名一旦进入报告契约，不因实现类重命名而漂移。

### 4.3 Terminal summary

终态报告必须同时保留：

- 端到端 `wallElapsedMs`；
- 各顶层阶段的 wall time 和累计工作量；
- CPG node/edge、规则 decision/edit、evidence/diff/write-back 计数；
- allocation、GC、working set 和 persistence hit/miss；
- DOP、queue wait、peak active 和 reorder/retained buffer；
- graph/rule/artifact snapshot identity 与等价校验结果。

终态 summary 是导航和回归入口，详细 per-stage/per-item 事件是诊断证据，两者不能互相替代。

## 5. 当前代码的归属边界

| 位置 | 性能组件可以读取或补充的事实 | 不应由它拥有的事实 |
| --- | --- | --- |
| `WorkspaceAnalysisService` / loader | restore、Workspace open、project selection、compilation/document snapshot 阶段 | Roslyn symbol 语义和规则决策 |
| `NLCPGBuilder` | 复用 `NLCPGBuildMetrics`、pass elapsed、anchor discovery、persistence、node/edge 和 cache facts | 改变 pass 顺序、NodeId、edge ordinal 或 capability |
| `PartitionedSyntaxPass` / `PartitionedOperationPass` | future 的 collect/materialize 分项和 partition counters | worker 直接写共享图或决定最终顺序 |
| `RuleGraphExecutor` / `RuleGraphAnalysisExecutor` | 复用 `RuleGraphNodeTelemetry`，按 Mark/Propagate/Lift/Propose 聚合 | 改变依赖图、输入端口、输出事实或调度语义 |
| `RuntimeMeasurementLog` | 输出轻量 runtime sample、阶段 summary 和 terminal fields | 重新计算领域 metrics，或因 sink 失败阻断分析 |
| `DirectoryAnalysisService` / artifact writer | diff、evidence、write-back 的独立 wall time 和字节数 | 重新排序或修改结果 materialization |
| Performance harness | warmup、measurement、DOP matrix、snapshot equality 和统计 | 放宽成功条件，或把不同输入合并为一个样本 |

现有事实优先复用：`NLCPGBuildMetrics` 已经有 `PassElapsedMilliseconds`、anchor/persistence metrics 和图规模；`RuleGraphNodeTelemetry` 已经有 input/output/elapsed/status；`RuntimeMeasurementLog` 已经有进程和 pool 采样。初版不复制这些数据结构。

## 6. 运行模式和采样规则

| 模式 | 默认采集 | 用途 | 是否进入正式中位数 |
| --- | --- | --- | --- |
| `normal` | terminal summary、5 秒进程 sample、低开销阶段事件 | 日常运行和故障上下文 | 可以 |
| `diagnostic` | per-stage/per-item、allocation delta、partition detail、规则热点 | 定位单个代表性输入 | 不与 normal 混合 |
| `profile` | 一份外部 CPU trace 或 counters，必要时限制并发 | 连接阶段和真实调用栈 | 不进入 normal 中位数 |
| `benchmark` | 固定输入、配置和输出，warmup 加测量样本 | 性能决策和回归比较 | 可以，需通过等价校验 |

初版沿用现有 harness 的 warmup 加三次测量。若后续采用 LNT 风格的丢弃预热或增加样本数，必须把策略写入 report metadata。`dotnet-gcdump` 只允许在隔离的 diagnostic run 使用，不能混入 benchmark 样本。

### 6.1 并发实验

至少保留以下矩阵维度：

```text
(directoryDop, cpgDop) = (1, 1), (1, 12), (12, 1), (12, 12)
```

每个样本同时报告：

- wall median/p95；
- pool accumulated elapsed、queue wait 和 actual peak active；
- allocation、GC、working set；
- node/edge、decision/edit 和 artifact snapshot。

累计并发工作量允许大于 wall time，也允许与多个操作重叠。任何报告都不能用累计值替换端到端裁决值。

## 7. 聚合和可信度

### 7.1 单次运行

对每个阶段和 item 计算 `wallElapsedMs`、`allocatedBytesDelta`、输入输出数量和结果规模。并发阶段再计算 `accumulatedElapsedMs`，明确标为工作量。阶段树需要保留父子关系，避免把 anchor discovery 或 persistence restore 重复加进正式 CPG pass。

### 7.2 多次运行

只有以下条件全部相同才允许聚合：

1. source/fixture、rule profile、capability fingerprint 和 SDK 相同；
2. cache mode、DOP、日志 profile 和诊断开关相同；
3. graph、rule、decision、rewrite 和 diff snapshot 等价；
4. 每个样本都有成功终态或被明确归类为失败/取消；
5. warmup 和 measurement 的样本语义相同。

报告至少输出 median 和 p95；样本少于三次时只输出原始值并标记低置信度。阶段汇总还要输出 sum、max 和 top item，不能只输出全局平均值。

### 7.3 归一化值

在同一输入内可输出：

```text
allocatedBytesPerNode = allocatedBytesDelta / max(nodeDelta, 1)
allocatedBytesPerEdge = allocatedBytesDelta / max(edgeDelta, 1)
stageMsPerSourceKiB = wallElapsedMs / max(sourceBytes / 1024, 1)
ruleMsPerOutput = wallElapsedMs / max(outputCount, 1)
```

归一化值只用于定位和横向解释，不能替代原始计时。分母为零时保留 null 或显式的 zero-output 状态。

## 8. 分阶段落地

| 阶段 | 内容 | 完成证据 |
| --- | --- | --- |
| P0 | 只定义 identity、stage vocabulary、summary schema；保持生产代码不变 | 文档、schema example、字段语义审阅 |
| P1 | 将 `NLCPGBuildMetrics`、anchor、persistence 和 `RuleGraphNodeTelemetry` 汇总到每文件结果和 terminal report | focused tests、稳定 JSON、失败不影响分析 |
| P2 | 为 Workspace、CPG、RuleGraph、artifact 增加父阶段和资源 delta；区分 wall/accumulated | Unit/Contract 覆盖阶段树、空值和异常 |
| P3 | 对 partition worker collection 与 ordered materialization 增加 diagnostic-only detail | 大文件 sample、DOP 1/2/16 图和结果等价 |
| P4 | 将 summary 接入现有性能 harness，增加样本聚合、top item 和性能自校验 | `summary.json/csv`、warmup/measurement、DOP matrix |
| P5 | 对代表性样本接入 `dotnet-trace`/`dotnet-counters`，独立运行 gcdump | profile attachment 与阶段 identity 可关联，常规样本无诊断开销 |

P1 到 P3 不应同时重写 CPG 并发或规则调度。先让证据完整，再用证据驱动单独的优化 feature。

## 9. 验收契约

### 9.1 语义不变

- 性能 sink 被禁用、抛异常或写盘失败时，分析结果仍按原契约完成或失败；
- instrumentation 不访问或修改 CPG、Roslyn semantic model、规则事实和 rewrite plan；
- DOP 1、2、16 的 graph、rule stage snapshot、decision、evidence、rewrite 和 diff 等价；
- graph 节点和边、规则输入输出、artifact identity 没有变化时，才能声明只发生性能改动。

### 9.2 报告稳定

- 阶段和 item 按稳定 identity 排序，不按完成顺序排序；
- schema version、run identity、sample mode 和 environment fingerprint 始终存在；
- unknown、zero、failed、cancelled、skipped 含义可区分；
- 文本和 JSON 由同一聚合结果生成；
- terminal summary 缺失时 harness 拒绝该样本，而不是从中间日志猜成功。

### 9.3 测试层级

- Unit：计时聚合、p50/p95、小样本、并发累计值、零分母和失败事件；
- Contract：schema、稳定排序、字段缺失/未知值和 report writer 一致性；
- Host：Workspace/CPG/RuleGraph/artifact 阶段边界、sink 故障隔离和 DOP 等价；
- Performance：固定真实源码、warmup 加三次测量、(1,1)/(1,12)/(12,1)/(12,12) 矩阵和输出快照；
- Diagnostic：代表性样本的 trace/counters/gcdump attachment 可定位到同一个 `runId` 和 `stageId`。

## 10. 暂不采纳的方向

- 不复制 `llvm-mca` 的 cycle simulation；NLISSN 的阶段是 C# Workspace、CPG 和规则图，不是 CPU instruction pipeline。
- 不让 `RuntimeMeasurementLog` 变成所有领域 metrics 的唯一 owner；它只负责低开销运行时输出和终态投影。
- 不把 BenchmarkDotNet 引入为整个端到端 harness；它只适合 Roslyn semantic query、cache 或 materialization 的受控微基准。
- 不默认开启 per-partition allocation、对象图 dump 或 CPU profile；诊断开销必须显式隔离。
- 不因为 Joern 或 CodeQL 有并发/性能组件就照搬其调度或查询语义；外部代码只提供结构启发。

## 12. 2026-09-10 事实传播补充决定

本节补充并覆盖本页早期只描述采集组件的抽象，作为当前实现的跨层依据。

### 12.1 两条传播通道

完成摘要使用不可变结果值逐层传播，供 normal 和 benchmark 使用：

```text
NLCPG -> CpgPerformanceFacts -> ApplicationPerformanceFacts
      -> DirectoryPerformanceFacts -> RunPerformanceReport
```

diagnostic/profile 模式可以使用可选 `PerformanceEventSink` 记录高基数 stage、partition 或 rule-node 事件。它不是 P1 完成摘要的依赖，不是共享全局 collector，且 sink 失败只能丢诊断数据。

### 12.2 结果载体和 owner

- `NLCPGBuildMetrics` 只属于 NLCPG。Application 在 `BuildFromSemanticModel` 返回后立即把它映射为中立的 `CpgPerformanceFacts`。
- `PrototypeAnalysisResult.Performance` 是可选的当前单项伴随对象，不包含目录 children 或 Run 级 wall time。
- `AnalysisRunOutcome` 同时携带业务 `PrototypeAnalysisResult` 和 `RunPerformanceReport`。
- Directory 保留逐文件 facts，并按稳定 Index/identity 聚合；Workspace 保留 project/TFM 层级。
- Host 创建 run identity、根阶段和 artifact，不反向访问 Builder，也不重新计算低层 metrics。
- 内部 facts、Run report 和外部 JSON DTO 分离；`summary.json` 由 Host/Infrastructure 显式映射生成。

### 12.3 时间、资源和比较

- 父阶段独立测量 `wallElapsedMs`；子项累计时间单独记录为 `accumulatedElapsedMs`。
- `GC.GetTotalAllocatedBytes`、GC count、heap 和 working set 默认只做 process/run/顶层阶段归因；并发文件级归因使用 `null`，除非 scope 独占。
- 未接通阶段使用 `unavailable`，配置跳过使用 `skipped`，无法可靠取得使用 `unknown`；真实测得的零才写 `0`。
- 报告记录输入、规则 profile、capability、cache、SDK、DOP、mode 和 snapshot identity。
- 不等价或不完整的样本保留原始 facts，但 `comparisonEligible` 为 `false`，不得进入性能统计。

### 12.4 Artifact、模式和阶段

新增 `artifacts.performance.enabled`，默认 `false`，与 runtime log 独立。启用后在 `<runRoot>/Performance/summary.json` 生成终态报告；报告采用原子发布，worker 不直接写最终文件。

阶段 identity 使用稳定协议名，例如 `CPG.Syntax`、`CPG.Operation`、`Rule.Propagate`、`Artifact.WriteBack`，不使用实现类名。完整阶段树先定义，P1 只接通已存在事实，其余阶段显式报告为 `unavailable`。

### 12.5 分阶段交付

P1 实现 CPG/anchor/persistence/pass、规则 telemetry 的单项与终态摘要；P2 接通 Workspace、Directory、Artifact 父阶段和资源 scope；P3 增加 diagnostic-only partition 细节；P4 接入现有 benchmark harness；P5 关联 trace、counters 和独立 gcdump。

P1 到 P3 不修改 CPG 并发、规则调度、admission、NodeId、edge ordinal 或分析语义。完整决策和验收标准见配套设计决策与执行计划。

## 13. Task 19 外部 profile 验证边界

2026-09-11 已加入 opt-in 的 `ExternalDiagnosticIntegrationTests`，验证代表性 Roslyn
fixture 在 profile 运行中可以把 `dotnet-trace`、`dotnet-counters` 和 `dotnet-gcdump`
的 attachment manifest 关联到同一个 `runId` 与 `stageId`。验证只检查 manifest 元数据、
稳定 tool 排序、相对 artifact 路径、工具版本和文件存在性，不对 trace、counter 或 gcdump
的内部内容做业务判断。

该验证需要开发机显式安装三个 .NET global tools，并设置
`NLISSN_RUN_EXTERNAL_DIAGNOSTIC_TESTS=1`。当前环境未发现这三个命令，因此真实外部 profile
样本没有宣称通过；focused test 会保留一个 manifest round-trip 通过项，并将工具 profile
项标记为带原因的 skipped。缺少工具不会被转换成零值或伪造的 available attachment。

验证 wrapper 使用临时输出目录、短时采样和进程超时；结束后清理临时目录。外部 profile
不进入 normal/benchmark 的性能统计，也不改变 CPG、RuleGraph、DOP 或分析结果语义。
